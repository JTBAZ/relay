## Handoff authority and user flow

Show **Review X handoff** on one scheduled confirmed draft, including drafts later deselected. Review reads its immutable BPX creation receipt, BPS schedule receipt, current adapter row and pinned JPEG from the same API instance. Require an authenticated owner, pending X event linked to the existing plan/variant, exact event title = confirmed `postText`, matching scheduled UTC time, preview-only variant media binding, and a live pinned JPEG whose bytes hash to the receipt. Display exact copy, actual thumbnail, scheduled London/UTC time, and “temporary mock handoff; X publication is manual.” Do not derive anything from current selection, preparation copy, source fixture or original media. Review writes no handoff record.

Add `POST /conversation/x-draft/handoff/review` with `{sessionId,revision,variantId}` and `POST /conversation/x-draft/handoff/confirm` with `{sessionId,reviewToken}` to the existing schedule router. A distinct signed token binds creator/session, one pending ID, revision/generation, draft identity, plan/variant/event IDs, source/export/copy/schedule hashes and ten-minute expiry (existing 8,192-byte token limit). A new turn, manual selection change, competing review, expiry, missing pin or changed event invalidates an unconfirmed review. Confirm uses the existing session `confirming` and mutation guards, rechecks the full binding after any await, and stores one immutable mock handoff receipt keyed to that scheduled draft. It does **not** modify the plan, variant, event, BPX creation receipt, BPS schedule receipt, JPEG or conversation choices. Bound successful token receipts to 64/session; the existing 32-draft/session and two-hour expiry cap handoff identities. Exact successful token retry returns the original handoff receipt plus the current snapshot even after later turns. A different stale token conflicts. If a handoff is already confirmed, show its receipt and an explicit **Open X again** control; one click may open one more compose tab, but no background retry or automatic tab open occurs. Failed extension delivery leaves the receipt intact so the creator can explicitly retry. No fill result is treated as publication.

After a successful Confirm, the bench may send one browser message from that button click; recovery uses the separate Open control. Extend `sendRelayScheduleEventToExtension`'s surrounding web pattern with a **separate strict mock-handoff helper** carrying only `{session_id,handoff_id,destination:'x'}` in `RELAY_CROSS_POST`. Do not send copy, JPEG bytes, bearer tokens, `content_override`, fake post IDs, or arbitrary URLs from the page. Keep the old strict `schedule_event_id` branch and its `bench_event_<64 hex>` validation unchanged: BPS uses `bench_event_<UUID>` and the existing DB package intentionally refuses mock IDs. The extension background accepts the new branch only from its existing trusted Relay web origins, fetches a read-only owner-authorized mock package, then uses the existing `runRelayCrossPostFlow` X tab open/inject path. The package has the existing X shape (`post_text`, one JPEG media entry, no attempt or original-media fallback); any required `relay_post_id` field is a mock transport handle only. The X fill script keeps its existing no-submit behavior and manual-publish banner.

## Exact JPEG transport

The development-only package and JPEG GET routes must live with, or read through a narrow callback into, the **same** schedule-router session/adapter state; do not create a second Next or server mock store. Inject an explicit extension-grant creator resolver from `src/server.ts`: require `Authorization: Bearer`, validate `SessionKind.extension`, map the grant to its creator, and reject cookie-only requests. The normal cookie auth used by Conversation must not take precedence for these routes. Resolve the opaque handoff ID plus owned session; recheck the confirmed receipt, pending linked event, source/export/copy hashes and pinned bytes for every package and media GET. Return only the exact confirmed `post_text` and one `image/jpeg` `bench_preview_*` entry with a narrow relative content URL. JPEG GET returns at most BPV's existing 1 MiB, `private, no-store`, `nosniff`, and 404/409 after session expiry, revocation, changed facts or missing bytes. No grant or signed token appears in the URL or browser message. These mock endpoints are 404 outside development; the existing real-Library schedule-event DB package route remains unchanged.

The current injected X script fetches media as `https://x.com` page-origin code; the local API preflight already returned 403. For **this mock JPEG only**, have the extension background fetch the exact package and its single allowlisted JPEG route with its Bearer grant, enforce the existing 1 MiB cap, JPEG MIME and raw SHA-256 from the package, and then open X. Inject one short-lived, **tab-bound packet** containing the parsed copy and verified JPEG bytes into the extension's isolated content-script world before injecting the existing X fill script. That script consumes the packet once and passes a `File` through its current image-attach path; it does not fetch the mock image from X. This avoids the existing global `pending_cross_post` storage race, where another handoff can overwrite the package while a tab loads. No raw JPEG in extension local storage or page DOM, no Bearer in the packet, no arbitrary URL proxy, no extra CORS allowance for `x.com`, and no manual-upload substitution claimed as success. A failed package/byte fetch opens no compose tab; a failed attach reports partial/failure and leaves publication manual. Keep the legacy global-storage and real-media fetch branches unchanged. Source-only work cannot prove X's current DOM accepts the image.
