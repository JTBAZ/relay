## Small edit contract

Only the approved posting text is editable in this slice: X `variant.postText`, or DeviantArt `variant.title`. The linked pending manual event's `title` must equal that text, so both fields change together. The existing due time, description/body, tags, selected media, platform settings, destination, source binding, plan/variant/event IDs, and note do not change. Accept a nonempty trimmed literal of at most 200 UTF-16 code units, consistent with the current manual-event title contract; also enforce the X platform limit. This is direct user-provided text, not a model interpretation or a new caption generator. No date edit or rescheduling API is included. The fixture's Europe/London posting-time contract remains as it is.

Add narrow `POST /api/v1/editor-bench/schedule/variant-edit/review` and `/variant-edit/confirm` handlers to the existing development-only router. Review takes **only** `{ variantId, expectedRevision, newText }`, reads the creator-owned mock draft and pending linked event from the existing per-API adapter, and returns old/new text, field-level diff, pinned source version, current revision, and expiry. It writes nothing. Unknown and other-creator IDs get the same uninformative not-found result; non-draft variants, non-pending or mismatched linked events, invalid text, and stale expected revisions refuse safely. A no-op returns a clear `unchanged` result **without a token** or history entry. Confirmation takes only `{ reviewToken }`; use the router's existing creator auth and mutation guard, but a **disjoint** compact HMAC edit token and verifier so the existing V1/V2/V3 creation `/confirm` rejects it. Bind creator, variant and linked identities, expected revision, old-text hash, exact bounded new text, pinned source fingerprint, and expiry. Keep the existing 8,192-character token bound and ten-minute TTL. Confirm rechecks ownership, draft/pending status, linked facts, source pin and expected revision inside the adapter's compare-and-set operation; a different stale review gets 409 and must be reviewed again.

Do not reload the latest fixture to rewrite the variant. Its immutable BPD-01 `bench_source_v1` snapshot and `approved_initial_variant` are the pinned original for every edit, even if the sample later changes. A copy-only edit is allowed against that pinned draft without silently rebasing. The review and history show that source version; no source post mutation, production Library read, or live database record is involved.

## Revision and retry semantics

Extend the **same** BPD-01 in-memory adapter, rather than adding another variant store. Preserve an immutable `creationRows` receipt and separate `currentRows` for each V3 identity. The existing exact V3 creation-token retry still returns its original creation receipt even after edits and never resets `currentRows`; a separately confirmed posting request still creates a separate trio. Add an additive namespaced revision record to the mock variant advice: revision **0** captures the initial approved field, creation time and pinned source version from BPD-01; each confirmed edit appends `{ revision, field, before, after, sourceVersionKey, sourceFingerprint, confirmedAt, editIdentity }`. Keep the BPD-01 creation snapshot/diff and every earlier revision immutable. Do not claim this is a general production audit system.

Edit confirmation atomically updates only the current variant text, the matching event title and their update timestamps, then appends one revision and saves an immutable receipt for that edit identity. Preserve the plan/variant/event IDs and all unrelated row fields. The exact edit token already applied returns **that recorded revision receipt**, without appending again, even if a later edit has advanced current state; it must not present the later text as the earlier edit's result. A different token based on an old expected revision conflicts. Clone data at adapter boundaries so callers cannot mutate history or current rows. No partial text/event/history update may survive a failed commit.
