# CP-06 — Deterministic compiler split (Frozen design)

**Status:** Accepted by parent architecture review, 2026-10-15. CP-04 typed contract is accepted; CP-05 interpreter is being implemented. CP-06a starts only after CP-05 acceptance. This document changes no runtime contract or code. The frozen [PLAN-CONTRACT.md](PLAN-CONTRACT.md) and [INTERPRETER-PLAN.md](INTERPRETER-PLAN.md) remain authoritative.

## Shared input and owned authority

CP-06 consumes the narrow CP-05 `InterpretedRequest`: at most six `add | revise | remove` intents with exact latest-request quotes, sparse `changed_fields`, selected or explicit source references, optional title/template/time/destination/action fields, root `base_revision`, and server-issued edit handles. It never interprets prose through a second keyword-only parser, calls a model, posts externally or writes Prisma. The compiler checks shape/quotes and authorized rows; quote containment is traceability, not proof of semantic understanding. CP-14/16 evaluate semantic errors separately.

Use the accepted `src/conversational-planning/contract.ts` exports directly: `PlanSnapshot`, `PlanStep`, `SourceRef`, `CopyValue`, `TimeSpec`, `DistributionGroup`, `UnresolvedRequest`, `Clarification`, `TrustedPlanContext`, `validatePlanShape`, `validatePlanWithContext`, `MAX_PLAN_STEPS=32`, `MAX_CLARIFICATION_SLOTS=16`, and `MAX_PLAN_BYTES=65536`. The contract requires every preview/distribution group to reference a `prepare_post_draft` source step. It allows a group with an original-media Patreon variant before preview, and requires X/DeviantArt teaser variants to depend on a preview step. It rejects a second destination variant in the same group and publication-relative social steps without a same-destination handoff. CP-06 builds those edges; it does not alter contract validation.

The trusted lookup interface is a **read-only test seam**; implement with mocked data in CP-06, and let CP-08 later supply creator-scoped Prisma queries. All returned rows retain their `creatorId`; a missing/foreign row is indistinguishable to a public caller and cannot be used as evidence. Suggested exact seam:

```ts
type SourceMediaRow = { id: string; creatorId: string;
  processingStatus: "READY" | "PENDING" | "FAILED";
  ingestOrigin: string; primaryPostId: string | null; postIds: string[];
  autopostDraftId: string | null; filename: string | null; mimeType: string | null };
type SourcePostRow = { id: string; creatorId: string; publishState: "draft" | "published";
  effectiveTitle: string; mediaIds: string[]; creativeWorkId: string | null;
  seriesMemberId: string | null; verifiedPartLabel: string | null };
type SourceTemplateRow = { id: string; creatorId: string; name: string;
  config: unknown; updatedAt: string };
type TrustedLookup = {
  loadMedia(creatorId: string, ids: readonly string[]): Promise<SourceMediaRow[]>;
  loadPosts(creatorId: string, ids: readonly string[]): Promise<SourcePostRow[]>;
  loadSourceRelations(creatorId: string, mediaIds: readonly string[]): Promise<ReadonlyMap<string, {
    postIds: ReadonlySet<string>; creativeWorkIds: ReadonlySet<string>;
    creativeSeriesMemberIds: ReadonlySet<string> }>>;
  loadTemplates(creatorId: string, ids: readonly string[]): Promise<SourceTemplateRow[]>;
  listTemplatesByName(creatorId: string, name: string): Promise<SourceTemplateRow[]>;
  destinationReadiness(creatorId: string): Promise<ReadonlyMap<Destination, "available" | "needs_credential" | "needs_extension">>;
  hasAutopostEntitlement(creatorId: string): Promise<boolean>;
};
```

The adapter supplies authenticated creator ID, selected IDs, request clock/timezone, current snapshot/handle map if editing, and a server-created source fingerprint. CP-06a converts loaded rows to `TrustedPlanContext` and runs `validatePlanWithContext` before returning a persistable snapshot. No model-supplied creator ID, source fingerprint, template config, part value, step/group ID, or connection readiness is trusted. This interface does not authorize an implementation to query all Library posts or bypass `creatorId` in CP-08.

## CP-06a — Source, copy, template and new-plan graph

**Owner:** Luna high; `src/conversational-planning/compiler.ts`, `tests/conversational-planning/compiler.test.ts` only. **Depends on:** accepted CP-04a and CP-05 interface, parent acceptance of this split. **Result:** `compileNewPlan(...)` plus a frozen `CalendarResolver` input interface for later CP-06b. The function returns exactly one of `{kind:"plan",snapshot}`, `{kind:"clarification_preview",slots,unresolved}`, or `{kind:"limitation",code}`. It must not return a fake valid snapshot when a source cannot be resolved.

Resolve selected `MediaAsset.id` to one creator-owned `Post.id` only when the selection and creator intent identify that post unambiguously. If several linked posts/work members remain possible, return `ambiguous_source` with no persisted plan and no invented IDs. A READY unattached staged media ID can be `SourceRef.kind="staged_media"`; it is not a `Post.id`, and distribution waits for a real post. For an existing post, use `SourceRef.kind="existing_post"`, the selected media relation, and only verified series-member metadata for a part. A `prepare_post_draft` source step can refer to selected attached art and an existing source post; it does **not** claim `AutopostDraft.mediaIds` already contains it. Set its `target_post_id` to that existing post only when the creator explicitly chooses to distribute the existing post. If the creator asks for a new primary post, `target_post_id` stays null until an authoritative new Relay post exists. If that new post requires attached art that the current draft service cannot reserve, emit a visible media/source repair requirement (using the frozen `missing_post` clarification where a post is the absent prerequisite) and keep the relevant preparation/handoff waiting. Do not mark it ready by creating a title-only draft. The compiler describes intent, not adapter execution state.

**Teaser-only source-reference gap:** A creator may ask only for X/DeviantArt teasers from an existing selected Post, with no new Patreon draft. The compiler may use that post's exact current metadata title as an **internal source label**; that title is not a requested rename, drafted copy, or authorization to create another primary post. The accepted graph contract currently requires `DistributionGroup.source_step_id` to name `prepare_post_draft`, but that capability has no discriminator between a real draft request and a reference-only helper. CP-06a must not silently encode the helper as a no-op `prepare_post_draft`, and CP-09 must not materialize an unnecessary `AutopostDraft`. Until the parent approves a narrow CP-04 contract amendment (for example an explicit source-step mode), return a typed `contract_gap` limitation for teaser-only compilation while preserving the selected source identity for review. Do not ask the creator to restate an unambiguous request merely to hide a schema gap. This is the one known contract decision to resolve before calling teaser-only graph compilation complete.

Build `CopyValue.mode="literal"` when the creator explicitly requests exact text, including literal `X`; otherwise use `part_substitution` only when explicit creator part or one creator-owned `CreativeSeriesMember.partLabel` proves it. Preserve bounded prefix/suffix, punctuation and title origin; unknown part becomes `UnresolvedRequest`/`unknown_part`, never a guessed series index. Resolve a saved template only by exact owned ID or a unique owned name, then `parsePreviewTemplateConfig`; missing/ambiguous name becomes `missing_template`. A template name in the model output is a reference candidate, not ownership evidence. No crop/export/preview media ID is produced here.

For a fully specified source and copy, assign server IDs once and construct source step → optional original-media Patreon distribution/handoff; source step → saved-template preview; source+preview → X and DeviantArt teaser distribution/handoffs in **one** `DistributionGroup`. The Patreon distribution step has `preview_step_id:null`, so it can become ready before Previewizer; X/DeviantArt require the preview step. Two explicit X publication-relative actions depend on the X handoff, each with exactly the selected `reply_block` or `engagement_check` and day offset. “Stoke engagement” alone yields inert `UnresolvedRequest` nodes and focused action/target slots. Unlinked X disables or leaves unresolved the X handoff and X follow-ups without dropping an independent Patreon/DeviantArt proposal; use only accepted clarification reasons and validate enabled dependencies. Missing template leaves teaser requests unresolved while the Patreon source/group portion stays useful. If user information needed for a valid source step is missing, return a clarification preview; if a teaser-only request is fully specified but the frozen source-step contract cannot represent it without implying draft creation, return the scoped `contract_gap` limitation above.

The new-plan compiler is allowed to create an absolute `TimeSpec` only through an injected resolver response. CP-06a tests inject a fake calendar resolver to verify graph placement without claiming real date/DST correctness. It calls `validatePlanShape` and `validatePlanWithContext` on every proposed snapshot. If the real `TrustedPlanContext` cannot be assembled from the owned lookup rows, report the precise missing row; do not weaken validation. No persistence, materialization, URL inference or external publication claim.

**Focused proof:** `npx vitest run tests/conversational-planning/compiler.test.ts` plus backend build. Positive: selected existing post with explicit primary draft, literal and proven part titles, Patreon-first group, saved template, separate X/DA variants, two explicit X follow-ups. Negative: unknown/foreign media/post/template, multiple post links, unattached staged media with no post, missing part/template, vague engagement, unlinked destination, visual request, duplicate destination, malicious filename/title, missing source, no image-derived copy, and an explicit primary draft sourced from existing art that falsely claims attached media. A teaser-only intent must yield `contract_gap` without creating a draft until the source-step discriminator is accepted. The tests show deterministic compilation of supplied intent, not model semantics.

## CP-06b — Calendar resolver

**Owner:** Luna high; new `src/conversational-planning/calendar-resolver.ts`, `tests/conversational-planning/calendar-resolver.test.ts` only. **Depends on:** accepted CP-05 time-intent shape and CP-06a's frozen `CalendarResolver` interface; no edit to `compiler.ts` while CP-06a runs. **Result:** pure `resolveAbsoluteTime(intent, requestClock, frozenCreatorZone, previousConfirmedTime?)` returning `{kind:"resolved",time: TimeSpec & {kind:"absolute"}}` or `{kind:"clarification",reason:"unknown_time"}`. No Prisma, reminders or publication evidence.

Resolve explicit local `YYYY-MM-DD HH:mm`; unqualified weekday means the next occurrence at supplied or previously creator-confirmed local time, including today only when that instant is still future. `this Friday` is Friday in the current ISO week; a past instant clarifies. `next Friday` is Friday in the following ISO week. Use the authoritative request instant and creator IANA zone, not process local time. Missing zone, time or an unconfirmed inherited time clarifies. Apply the frozen CP-04 policy for nonexistent spring local times (advance to first valid local time that day) and repeated fall local times (earlier occurrence), verifying whether the existing `zonedLocalDateTimeToUtc` helper actually satisfies it; add a narrow resolver if not. Return UTC instant *and* concrete local date/time/zone for plan review; never add 24-hour milliseconds for calendar days. Publication-relative offsets remain unresolved until evidence in CP-13 and are not computed here.

**Focused proof:** `npx vitest run tests/conversational-planning/calendar-resolver.test.ts` plus backend build. Test Europe/London and at least one other IANA zone, unqualified weekday today cutoff, this/next ISO-week boundaries, year rollover, explicit date, missing time/zone, prior confirmed time, spring gap/fall fold, invalid date, no process-timezone dependence, and exact local/UTC round trip. Keep timezone fixtures deterministic with a supplied clock.

## CP-06c — Revision handles and sparse field patches

**Owner:** Luna high; new `src/conversational-planning/revision-merge.ts`, `tests/conversational-planning/revision-merge.test.ts` only. **Depends on:** accepted CP-05 add/revise/remove shape and CP-06a's frozen compiler input/output/ID policy; may run in parallel with CP-06b after CP-06a acceptance because files are disjoint. **Result:** pure `mergePlanRevision(current, handleMap, intent, latestUserText, expectedRevision)` returning a field-level patch or explicit conflict/clarification. The caller then recompiles/revalidates the new snapshot. No Prisma write or direct mutation of authoritative drafts/events/attempts.

Handles are server-issued aliases bound to `(creatorId,planId,revision,stepId)` and never raw model-generated IDs. Require root `base_revision` match, each revise/remove handle map to a current step, exact request-quote containment, and a supported `changed_fields` list. `null` outside that list means unchanged; an explicit clear requires a valid field-specific operation. Apply title/time/template/destination/enabled/action/target edits only where the latest request supports them. An unqualified target such as “move the teaser” when both X and DeviantArt teaser steps exist returns a target clarification; do not choose by title similarity or positional order. Preserve manual changes to all other fields, untouched sibling steps and prior IDs. Replacing a target/destination may mint a new step ID but must explicitly reroute or block dependents; remove cannot leave dangling edges. A no-op retry returns unchanged, while stale revision or conflicting expected values returns conflict. `PlanSnapshot.review` and execution pointers are not patchable by model intent.

**Focused proof:** `npx vitest run tests/conversational-planning/revision-merge.test.ts` plus backend build. Test exact handle binding, duplicate/missing/foreign handles, stale base revision, add/revise/remove, null-outside-mask preservation, manual title/time/template edits, explicit enabled change, target/destination replacement and dependent repair, ambiguous teaser target, duplicate delivery, no mutation of input snapshot, and no model-selected authority status.

## CP-06 integration gate

After CP-06a/b/c are individually accepted, **one** Luna high builder revisits `compiler.ts` and its focused tests to wire the real calendar resolver and revision merge. This serial integration is required before CP-06 can be called accepted; no concurrent worker edits `compiler.ts`. Run the three focused test files and backend build once after wiring. Verify the end-to-end *pure* journey: new plan, concrete upcoming weekday visible in review, creator manually changes a teaser title, a follow-up turn moves only the X teaser to the requested day, stale handle rejected, and all unaffected copy/steps preserved. Keep the Patreon plan step independent of preview and both X social steps dependent on qualified X publication intent. Re-run `validatePlanWithContext` on the final snapshot and report unresolved slots. No broad whole-repo suite, browser journey, paid model call, database migration or external posting belongs to CP-06. CP-07 persistence and CP-08 API remain blocked until the parent architecture review accepts the integrated pure compiler.

At most two builders run concurrently and only for disjoint CP-06b/CP-06c files after CP-06a freezes its API. Each sub-ticket reports exact changed files, focused command/result, one negative case and remaining gap. The parent accepts CP-06 as a whole only after the integration gate; a passing sub-ticket is not the final compiler gate.

**Deferred CP-11 adapter risk:** `reviseScheduledPostDistributionPlan` reads existing variants before its write transaction and skips siblings based on those earlier statuses. A concurrent creator handoff may change a variant after that read. CP-11 must re-read/lock within its transaction or use a conditional update guard before revising a draft; static status skipping alone does not prove a posted/handed-off Patreon variant is safe. This is distribution-service work, outside every pure CP-06 sub-ticket.
