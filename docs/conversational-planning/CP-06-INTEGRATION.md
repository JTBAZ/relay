## Result and boundary

Expose a pure `compilePlanRevision(...)` entry point alongside `compileNewPlan(...)`. Its trusted inputs are the current `PlanSnapshot`, authenticated creator ID, server handle map, expected revision, CP-05 `InterpretedRequest`, exact latest user text, server request clock/frozen creator timezone, a **fresh server-computed source fingerprint**, creator-scoped `TrustedLookup`, server-supplied confirmed times keyed by current step ID and scoped to the same creator/plan/revision, the real `createCalendarResolver()` (or the frozen resolver interface for deterministic tests), and server ID/time factories. It first calls accepted `mergePlanRevision(...)`; forward `conflict`, `clarification`, and `unchanged` without synthesizing a snapshot. For a `patch`, apply only its operations to a copy of the current composition, run `validatePlanShape` and `validatePlanWithContext` with a newly loaded context, and return a validated proposed revision or a precise conflict/clarification/limitation. Caller-side CP-07 compare-and-swap is still required; this function writes nothing.

Do not feed revision intents into `compileNewPlan` and replace the old snapshot with its output. That path assigns new IDs, reconstructs a graph from a maximum of six current requests, and would erase manual fields, sibling variants, clarifications, and stable references. Do not splice pieces out of a newly compiled full snapshot either. The smallest reusable seam in `compiler.ts` is to extract its existing creator-scoped lookup/context construction and final validation into private helpers used by both entry points. Extract a small **step-fragment** construction helper only where a supported add needs the same source, copy, template, readiness, and ID rules as new-plan compilation. It appends to an existing group; it never allocates a replacement plan/group or interprets prose again. `calendar-resolver.ts` and CP-06c retain their accepted responsibilities.

The revision function must preserve `plan_id`, `creator_id`, `source`, `created_at`, `review`, every unaffected step/group ID and field, and the current order except for deliberate new nodes. Advance `revision` exactly once for a changed, validated proposal and set only `updated_at` from the server clock. Do not accept model supplied IDs, source fingerprints, review states, authority pointers, status, publication evidence, template config, or connection readiness. No model, Prisma, network, Previewizer, distribution service, or publication call. Apply only while `review === "proposed"` in this pure gate; changes to approved/materialized plans need CP-07/09 authority-aware handling and should return an explicit safe limitation/clarification instead of pretending that a composition edit changed an existing draft or handoff.

## Patch application rules

1. Check the accepted patch's `(planId, baseRevision)` against the exact current snapshot again. Before each field write, compare `RevisionFieldChange.expected` with the current field, including the current `copy_title` for a distribution title. A mismatch is a conflict with the current snapshot; never overwrite a manual edit. Absent fields and `null` values outside `changed_fields` mean **leave unchanged**. Do not turn a request to move one step into a rewrite of any sibling.
2. Resolve a `time` change with the real `createCalendarResolver()` from CP-06b, passing only the server request clock and the targeted step's previously creator-confirmed absolute time. `PlanSnapshot.time` alone does not prove creator confirmation: use the optional server-supplied confirmed-time entry only when its creator/plan/revision/step binding and absolute value match the current target. For “move the X teaser to next Friday,” inherit that confirmed local `HH:mm` if the request omits time, even when another explicitly masked field is also revised. If the target has no trusted confirmed time, the zone is missing, the interpreted zone disagrees with the frozen zone, or the resolver returns null, return `unknown_time` clarification without a new snapshot. Keep the resolver's concrete `local`, `timezone`, and `at_utc` in review; do not compute dates in the patcher or use the prior time of another step. The CP-06b adapter already rejects model-zone mismatch; integration must actually call it.
3. Bounded `revise`: apply explicit `title`, `time`, `template`, and `enabled` only to the compatible target. For distribution title, update its own `title` and `copy_title` as one semantic field; keep other nodes' titles, including manually edited copy, unchanged. Template changes require one owned, parsed saved template and affect only the targeted preview node; if changing it would require silently rewriting dependent variants, clarify. An explicit disable with enabled dependents must ask for a repair choice rather than silently disabling siblings or returning a generic validation failure. Destination, target, and social-action replacement remain CP-06c's `dependent_repair_required` clarification until a separately reviewed dependent-repair contract exists.
4. Bounded `remove`: remove a terminal step only when CP-06c accepted it and no dependency or group reference survives. For a terminal follow-up this is straightforward. A distribution, preview, handoff, or source step with dependent or group edges asks for dependent repair. Never delete a node and leave dangling IDs, nor silently remove a sibling variant. Keep retained group IDs and `destination_step_ids` intact.
5. Bounded `add`: allow an explicit new publication-relative `reply_block` or `engagement_check` only under its existing, unique same-destination handoff with creator-selected action, target, offset, local time, and frozen creator zone. Allow an explicit new X/DeviantArt teaser variant only when the existing source and **one** existing group/preview with the same owned saved template make its dependency path unambiguous; mint IDs only for the new variant and handoff and append the variant ID to that group's list. Respect destination uniqueness and connection readiness. A missing preview/template, new primary draft, second group/source, changed target or destination, or requested graph reconstruction receives a focused clarification/`contract_gap` limitation as appropriate. Do not manufacture a `prepare_post_draft` helper for teaser-only plans; that known CP-04 discriminator gap remains open. Adds must not use a temporary full-plan compilation whose IDs or defaults could replace manual state.

For new-plan compilation, keep the current Patreon → Previewizer → X/DeviantArt group shape and explicit X social actions. Make three narrow corrections while touching `compiler.ts`: use only the trusted frozen zone for publication-relative social `TimeSpec` and clarify a conflicting model zone; honor `intent.enabled === false` on teaser distribution and its handoff instead of hardcoding the distribution enabled; and attach an `unlinked_destination` clarification to an unavailable Patreon handoff just as for X/DeviantArt. The contract disallows an enabled child of a disabled dependency, so propagate the requested disabled state through only that newly built dependency chain or ask for a focused clarification where doing so would affect an independently requested sibling. Revision edits must never silently propagate a disable across existing nodes. No new field or authority is needed.

## Final trusted validation seam

Move the existing `TrustedPlanContext` assembly at the end of `compileNewPlan` into a private helper taking the **candidate snapshot** and trusted lookup. At revision time, re-read exactly the candidate's source media and relations, source/target posts, all referenced template IDs and current configs, destination readiness, entitlement, and the server's current source fingerprint under the authenticated creator ID. Validate every returned row's shape, uniqueness, relation, and `creatorId`; a missing or foreign row must never become an owned set member. Do not query all Library posts or use old context captured when the plan was first compiled. Include all template IDs from retained preview steps, not just a newly added or revised template. The shared finalizer calls `validatePlanShape(candidate)` and `validatePlanWithContext(candidate, freshContext)` before returning `plan`. A changed source fingerprint, template config, ownership, or entitlement yields a scoped failure with **no snapshot**; do not silently rewrite the snapshot's source fingerprint or template config to make it pass. Preserve unresolved requests and clarification slots unless the accepted patch explicitly resolves their referenced issue; no general cleanup of old slots by inference.

The current compiler's context is built inline from the new plan's one loaded post/template and then immediately validated. Reusing that single-template context for revision would fail retained multi-step state or, worse, omit a stale retained reference. This is the reason for the private helper refactor. Keep `TrustedLookup` read-only and creator-scoped; CP-08 will provide the database adapter later.

## Architecture questions to report, not silently settle

- CP-04 still cannot represent a teaser-only source reference without implying a primary draft; keep `contract_gap` until a narrow source-step mode is reviewed.
- CP-05/CP-06c provide no dependent-repair list or expected-value token from the model. CP-06c's server-carried expected values are enough for sparse compatible edits; target/destination replacement and removal with dependents need a separate reviewed graph-repair shape.
- Pure CP-06 has no authority pointers or prepared/posted status. The proposed-only gate prevents a compiler return from implying that a prepared draft, existing distribution variant, handoff, or completed publication was changed. CP-07/09 must define the later authority-aware edit path.
- The snapshot does not carry time-confirmation provenance. This integration accepts an optional trusted, revision-scoped confirmation input and clarifies when absent; it does not persist a new field. CP-08 must define how its adapter derives that evidence without treating every proposed time as confirmed.
