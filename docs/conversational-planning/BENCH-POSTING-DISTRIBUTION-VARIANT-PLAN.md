## Contract and narrow seam

Extend the existing development-only `POST /api/v1/editor-bench/schedule/review` and `/confirm` for the `direct_manual` single-item path when an injected mock distribution adapter is configured. Keep the existing response's `review`, `reviewKind`, `reviewToken`, `expiresAt`, and confirmed `event` / `reused` fields; add a readable variant preview on review and a plan/variant receipt on confirm. Existing clients may ignore the additive fields. Use a strict HMAC V3 claim limited by the existing 8,192-character token bound: creator, expiry, validated event payload, selected fixture post and ordered media IDs, source version key/fingerprint, and hash of the exact proposed variant fields. The token carries no full snapshot or arbitrary model output. V1 and V2 token formats, IDs, validations, and confirm handling remain unchanged.

Derive a server-owned source snapshot from the effective fixture post version: fixture revision, selected post ID, effective title/description/tag labels, and the selected ordered media IDs with their relevant metadata. Give it a stable namespaced version key plus SHA-256 over canonical serialization. Fixture revision alone is insufficient because those rows have no PostVersion ID or sequence. Review is side-effect-free. At confirm, reload the source through the same injected fixture loader and recompute both hashes; refuse a changed, missing, foreign, or no-longer-associated item and require a new review. Bind the literal reviewed title and due time as already grounded by `manual-posting-event.ts`. Do not accept source copy, variant fields, post IDs, or media metadata supplied by the client. A later source edit must neither change the approved variant silently nor be bypassed by an idempotent readback.

Extract only the plan/variant draft **row construction** from `createPostDistributionPlan` into a small shared distribution helper used by both that existing service and this adapter. Keep the real service's own ownership, entitlement, active-plan, archive, media-preview, assistant, and transaction behavior intact; the mock branch must not call that service with `bench_*` IDs. Start from `formatPlatformVariant` and normal destination validation, then apply the explicitly reviewed posting text: for X, `variant.postText` equals `title_text` exactly; for DeviantArt, `variant.title` equals `title_text` exactly. The same literal remains `event.title`. Do not append tags or canonical body to X's approved text, synthesize a caption, or silently replace the creator's title with the formatter baseline. Retain other supported formatted fields only where they do not alter that approved text. Check the final X 280-code-unit and destination field limits before offering confirmation. The review displays both the source and final variant values and their field-level differences.

The opt-in adapter owns one per-API-instance, development-only in-memory store with Prisma-shaped plan, variant, and event records. It uses the shared row builder and an atomic commit/readback seam; it is **not** a new variant entity or a second publishing workflow. A confirm creates exactly one draft variant under one plan and one linked pending manual-event receipt, all or none. The link is stored and returned with the rows; the event has `post_id:null`, so no synthetic ID enters a real foreign-key table. Derive a deterministic V3 identity from creator, approved payload, source version, selected media, and variant hash. Repeating the exact valid confirmation returns the same linked records (`reused:true`); the same identity with mismatched saved facts conflicts. A distinct reviewed posting request, including another X or DeviantArt request for the same original, creates a separate trio without overwriting or archiving earlier mock records. Failure before commit leaves no partial rows. This mock adapter never calls Prisma, `createCreatorScheduleEvent`, a distribution attempt, Postbot, export, or publication. Its receipt is ephemeral across API restarts and must not be described as a durable Schedule Rail event. Normal DB-backed V1/V2 routes remain available when the adapter is absent; do not change UI or claim persisted rail behavior for the mock receipt.

Store a versioned, immutable `bench_source_v1` creation fact in the existing plan/variant JSON fields, not a new table or schema column. Include the source version key and fingerprint, bounded source snapshot, exact approved initial variant fields and selected media order, event link, and field-level `before`/`after` differences between the canonical source/formatter baseline and the approved initial variant. This proves which source version and explicit posting-text change produced the draft. It is **creation provenance only**, not edit history; this ticket adds no variant edit operation or claim to track later changes. Do not alter the fixture's post, version, media, tags, or staged `manualActions`.
