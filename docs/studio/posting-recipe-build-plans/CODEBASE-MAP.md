## Proposed ownership / schema direction (not a migration)

Freeze exact names and relations in P0 before writing Prisma:

- **CreatorPostingRecipe**: mutable lifecycle, active immutable revision pointer, trigger account/filters, activation/paused eligibility windows, independent Always-on mode, contextual Default selection, owner and optimistic version. Keep per-context Default uniqueness explicit; saving/default selection do not create runs.
- **CreatorPostingRecipeRevision**: immutable normalized trigger/filters/routes/copy/template/account/timezone configuration, unique `(recipeId, revision)`. A route keeps its ID across edits; anchor edges point only to earlier route IDs.
- **One-shot plan intent**: immutable config/target plus atomic next-match consumption or selected-artwork correlation. Reuse canonical action authorities; do not invent a parallel general plan execution engine.
- **Artwork enrollment**: immutable source acceptance/correlation record keyed by `(recipeId, sourcePublicationIdentity)`, pinned revision/source version/image. No mutable duplicate posting state. This prevents recipe edits from re-enrolling old artwork.
- Each revision/route/destination owns a `CreatorDistributionRule` and extends `CreatorDistributionRuleRun` with recipe/enrollment/route/destination correlation, frozen media/copy snapshot and predecessor-action/receipt pointers. One rule per destination keeps the existing unique rule/source constraint meaningful. Legacy discovery/materialization must skip rules with this ownership unless invoked by the recipe coordinator.
- **Distribution scope**: unique `recipe_action_key` on scoped plans, using the same stable action identity as the rule run. Legacy calls retain legacy behavior only within their own scope. Extend all lookups, package creation, revision and presence projections to avoid “latest active plan” ambiguity. Inspect conversational group scope and coordinate the shared seam; do not overload its key with recipe values.
- **Publication receipt**: canonical attempt fields plus append-only evidence projection where needed, keyed to action/destination with first-accepted anchor and evidence kind. External status stays authoritative on the attempt. The receipt is evidence, not a parallel attempt status table.
- **Notification outbox**: unique notice identity; receipt-derived payload; independent send/retry state.

No `CreatorAutomationRun`, second scheduler, generic workflow executor, second copy of distribution packages, or generic node schema is required. Recipe configuration and enrollment are new responsibilities; actual execution continues through established authorities.

## Important implementation traps

1. Existing `CreatorAutomation.distributionRuleId` is one-to-one. A multi-stage recipe cannot be wired through `createAutomation` with only a JSON editor change.
2. Existing discovery has no recipe activation cutoff and uses the latest version publication time. Importing history or editing old art must not trigger a new release.
3. Current Full routing resolves canonical media. A later source edit can change what “original” means unless explicit frozen selection is carried into the package.
4. The legacy plan-create operation can archive another active plan for the artwork. Scope isolation must ship before concurrent recipe stages or recipes.
5. Current `crossPostBluesky` is text-only and formats a base source package rather than executing an approved image variant. It is not an unattended art connector.
6. Template persistence omits crop. A “saved template” cannot by itself render every future image correctly.
7. Existing automation completion can mean successful handoff, not publication. No publication-relative route may use that completion timestamp.
8. Email's log provider returns `ok:true`. Delivery UI needs transport identity and provider receipt, not just `ok`.
9. Account email verification is not a local boolean on the inspected schema. PR-601 must resolve actual verified ownership (using the linked identity provider where supported); do not silently mail an unverified address or build a new identity system inside recipe scope.
10. Source-relative routes may select different destinations; only a publication-relative route needs its target accounts to exist in the chosen predecessor. Do not retain the old global row-2-subset restriction.
11. Existing Coach supports reviewed suggestions; it is not an unattended permission grant. Default/Always-on enrollment flags likewise do not authorize delivery.
12. Remote-review tokens, a creator mobile review page and cancellation-window claims are new responsibilities for P8/P9. Existing email transport and the extension cannot implement remote automatic posting by themselves.

13. Revision 3 defaults new timers to elapsed N×24h. Persist explicit timing mode rather than hiding a 09:00 calendar clock. Existing saved clock-based actions must retain their original meaning; optional clock mode still uses tested calendar helpers. Post display labels are derived, while dependency IDs remain stable.

14. Revision 4 requires independent description-source and Coach-enabled fields. Shared saved text is immutable from a route editor; custom text belongs to its route and is snapshotted at enrollment. Legacy exclusive Coach mode maps to original description plus Coach enabled. Selecting stock/custom text must not disable Coach or overwrite siblings.

15. Revision 5 removes disclosure-only time gating: opening Options does not select a time; blank/Clear means elapsed mode. Description is its own original/edit/saved selection. Seed an edit only once from the actual selected source (demo sample text is never a production source); preserve route custom text when changing selection. This remains a literal replacement, not a general text diff/merge engine.

16. The inspected `src/conversational-planning/calendar-resolver.ts` resolves absolute local dates and weekdays; zone conversion helpers are private. It has no recipe month-boundary resolver. Add a bounded first/last current/following-reference-month spec and tested adapter, with invalid past targets held per action. Do not call a weekday helper proof of month support.
17. A reusable description library is proposed configuration, distinct from execution drafts (`autopost-draft-service.ts`). Add creator-owned immutable description versions; freeze a selected version into recipe/action copy. Create/edit-as-new must not materialize posts or mutate shared accepted copy. Source-text availability, not merely a scheduled post row, gates Edit original.
