## Implemented boundary

The [health service](../../../src/patreon/patreon-sync-service.ts) now reads persisted creator/campaign binding, credentials, saved probes and completeness. The authenticated HTTP GET uses read-only session/account resolution and `Cache-Control: private, no-store`. Opening or refreshing health performs no provider request, OAuth refresh, cookie pruning, session renewal, work claim, repair seeding or dispatch. A campaign query cannot establish binding. Missing tokens or binding return an additive unavailable response with nullable OAuth fields. The existing [worker](../../../src/patreon/incremental-sync-worker.ts) uses the separately named maintenance method and retains bounded discovery and proactive refresh before provider work.

[Completeness](../../../src/patreon/sync-completeness.ts) reads existing post-progress JSON, roster state, current canonical heads, repair rows and accepted access receipts. Timestamped terminal archive checkpoints establish the known population. Capped populations remain bounded; one verified post or all currently discovered media cannot prove a partially scanned campaign complete. Legacy rows without accepted verification time remain unknown. Failed work counts are independent of the five displayed retry controls, including failures outside the canonical sample and first-ingest failures without a repairable head. Missing dependencies make affected evidence unavailable. Prior accepted verification survives a later failed attempt without refreshing its time.

Post/access receipts use the existing canonical idempotency storage under a distinct namespace, keyed by creator/post/current head/source. Targeted refresh, reconciliation, catch-up and access-only acceptance write inside the owning canonical transaction after existing ownership, campaign, current-head and lease guards. Old source receipts and unrelated replay markers remain separate. Queries inspect at most 100 canonical posts, 100 media and 25 unfinished change rows, with explicit bounded scope when capped. No schema or ownership-policy change was added.

[Health writers](../../../src/patreon/patreon-sync-health-store-db.ts) serialize the shared row's read/merge/write transaction, preserving a concurrent saved probe and the last accepted verification. File writes use a lock and atomic replacement. Freshness follows the existing 15-minute catch-up, six-hour reconciliation/member and 24-hour media expectations. Legacy edit admission remains unchanged; completeness attention is separate from the existing degraded/failed write gate.

The new authenticated resource-scoped `POST /api/v1/patreon/repair` validates current creator/campaign/head/generation, retains provider backoff and deduplicates pending/running work. It acknowledges scheduling with `completed:false`; provider work stays in the existing worker. PS-12 discovers successful cookie capture during the next bounded sync or sixty-second repair pass. Consent and health handlers start no inline repair.
