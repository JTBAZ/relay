## Accepted revision and bytes

[ExportService](../../../src/export/export-service.ts) uses creator-scoped canonical loads. Downloads have bounded retries, body timeouts and a 500 MiB decoded-byte cap. Identity-encoded responses also require matching Content-Length; Fetch-decompressed responses retain their decoded-byte cap. A stalled or cancelled body cannot publish partial bytes.

New local and R2 blob paths include revision identity and a content digest. Local writes use a unique temporary file, fsync and rename. [Guarded acceptance](../../../src/export/media-repair-store.ts) rereads the same creator, active media head, version sequence, revision, URL and prior key under the existing canonical creator lock. It commits currentStorageKey, matching version metadata and claimed-work completion together. It never saves a fetched full canonical snapshot. Stale success, failure and expired leases cannot overwrite current metadata or clear newer success.

[DB canonical hydration](../../../src/ingest/canonical-store-db.ts) restores matching export proof into the current version. An inherited storage key alone does not become proof for a newer revision. [Export indexes](../../../src/export/export-index.ts) expose the same accepted metadata to readers. Hosted readiness additionally checks R2 HEAD or readable local bytes and length, with eight concurrent checks and a shared three-second deadline. Unverified checks remain missing. Paginated Library reads verify selected-page media; GETs enqueue or persist no repairs. Known stale or deleted file-index entries are excluded from ZIP; unknown legacy file entries retain their read and missing-file 502 contract.

Hosted ZIP reads existing R2 objects without requiring an API-local copy. Each R2 entry must pass through the archive before the next buffer is retained. Disconnects abort in-flight object/body reads and the archive. ZIP preflight uses the same bounded presence view; objects unverified within its deadline retain the missing-file 502 response. Content, preview, thumbnail, manifests and Library Retry keep their existing HTTP contracts and access checks.

## Durable repair

The additive [migration](../../../prisma/migrations/20261020040000_patreon_media_repair/migration.sql) adds one tenant-bound repair table with cascade deletion, RLS and privilege revokes. It stores current head fingerprints, generation, due time, leases, retry counts and safe error codes. Blob records stay in MediaAsset version metadata. No cookies, tokens or raw provider responses enter repair state.

Scanning advances through 25 active Patreon posts at a time, independently of discovery watermarks and newest-post probes. A persisted creator cursor selects up to five creators per tick. Each creator processes four source/blob claims by default, capped at ten; a 90-second deadline prevents starting further claims. Individual requests retain their own time and byte limits. Five-minute leases recover abandoned attempts, failures back off to six hours, and completed work becomes eligible for verification after 24 hours.

Locally deleted, native or missing resources leave the claim queue as obsolete after an eligibility check under the canonical creator lock. Retirement requires the current lease, head and generation. It records no completion proof or upstream deletion. A restored resource requeues with a new generation even when its head matches the retired work.

[Source collection](../../../src/patreon/patreon-sync-service.ts) reuses PS-09 campaign ownership, access-first acceptance and observation fences. Missing consent stays retryable; late cookie consent wakes waiting source work. Expired download URLs get one current-source refresh and retry. Source refresh suppresses automatic export recursion and publication events. Proof is checked before optional autoexport can perform its own legitimate URL renewal.

[Cookie completeness](../../../src/patreon/cookie-scraper.ts) distinguishes explicit empty media from missing relationships, unresolved resources, unusable URLs and malformed embed fields. OAuth zero media alone stays unknown. Complete source proof is accepted only against the committed current post head. Verified empty collection, verified media collection and completed blobs remain separate states.

The [BullMQ scheduler](../../../src/jobs/schedule-bullmq-repeat.ts) registers a separate 60-second repair tick whenever shared persistence is configured, even when incremental autosync is disabled. [Workers](../../../src/jobs/register-workers.ts) consume DB state after restart or lost dispatch. Ordinary accepted sync also performs a small repair pass. Independent periodic repair requires BullMQ; the memory backend has no separate repair timer.

## Compatibility and rollout

Hosted repair requires shared canonical DB and credentials plus R2, or an explicitly verified persistent shared local root. `RELAY_EXPORT_SHARED_LOCAL_ROOT=1` is accepted only with an explicit export root. Equal path strings do not establish sharing, and R2 does not supply file locks.

File mode retains manual Retry and exports. FileExportIndex locks the complete read/merge/atomic-replace operation, treats corruption as an error, and initializes only ENOENT. This does not add a cross-process canonical-file guarantee or durable automatic file repair. Native upload, SubscribeStar, curation, shared-parent access and media audit identities retain their existing lanes.

Drain old mutable-path/index writers before enabling the new reader/worker behavior. Legacy imported media stays unknown until checked. Existing pilot seed storage-only rows require bounded idempotent fixture replay before reader cutover. Both [seed writer](../../../src/pilot-ux/seed-pilot-ux-dev-accounts.ts) and [simulator](../../../src/pilot-ux/pilot-ux-onboarding-walkthrough.ts) derive ordinary proof only from actual existing object bytes; missing objects remain missing. Full-seed membership compatibility belongs to the separate PS-10 platform-projection correction and its connected seed/feed checks; the isolated media replay regression proves only the media path.

Unaccepted immutable objects are retained. No automatic orphan sweep was added. Cleanup needs a grace period and proof that neither current nor retained versions reference a key; the existing purge worker does not establish that proof.
