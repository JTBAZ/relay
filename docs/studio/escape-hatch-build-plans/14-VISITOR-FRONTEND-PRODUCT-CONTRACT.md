# Visitor frontend product contract

## Purpose and authority

This contract defines the production patron experience generated by Escape Hatch. It resolves visitor-route, content-shape, search, media, paywall, tier-conversion, branding, and acceptance decisions before tier mapping and the operating CMS make those choices expensive to change.

The generated site is a creator-owned Patreon-like membership site, not a Relay network surface and not a general storefront or page builder. Posts are the primary content unit. A post may contain inline media and secure downloadable attachments.

When visitor-facing requirements elsewhere in this program conflict with this file, this contract governs. Identity, entitlement, private-media, billing-policy, provider-policy, and origin-data security rules remain non-negotiable.

## Gate

- EH-051, EH-052, and EH-053 may proceed because their provider boundaries do not depend on final page composition.
- EH-054 may not pass until its tier mapping, checkout entry points, and duplicate-billing safeguards conform to this contract.
- EH-060 and EH-061 may not pass until the post schema, gallery state machine, media behavior, tier catalog, and patron-facing preview states conform to this contract.
- `productionSafe` remains `false` until the applicable security, browser, sandbox, deployment, and human-signoff gates pass.

## Product job

The patron site has one primary job: help a fan discover a creator's work and receive the correct content for their active access, without exposing premium bytes or pushing an already-entitled patron into duplicate billing.

The creator-facing job is separate: Hatch Console lets the creator publish, preview, and operate the site. Operator controls never appear in production patron chrome.

## Design direction

### Design read

A cold-gallery membership site for a creator's patrons, with media-forward posts, unified membership conversion, and restrained chrome that lets creator work carry the visual identity.

### Design dials

- `DESIGN_VARIANCE 7`: asymmetric feature mosaic, disciplined feed, strict single-column mobile fallback.
- `MOTION_INTENSITY 4`: state and interaction feedback only; no decorative scroll choreography.
- `VISUAL_DENSITY 4`: breathable gallery presentation with compact search and access utility.

### Default token system

- Gallery black: `#0e0f12`
- Raised charcoal: `#16181d`
- Cool white: `#e8eaed`
- Muted steel: `#8b919a`
- Cobalt action: `#4a7fc4`
- Structural border: `#2a2e36`
- Display: Outfit
- Body and utility: Source Sans

The creator may publish one fixed scheme using the approved color schemes and type pairings. The patron does not toggle the scheme in v1. Accent, logo, density, crop, and paywall copy remain controlled dials. Raw CSS, custom scripts, arbitrary blocks, and a general page builder remain out of scope.

The signature is a two-state gallery:

1. At rest, creator-pinned feature posts form a mosaic above a reverse-chronological recent-post feed.
2. A non-empty search query or any active filter replaces both curated sections with one full eligible-gallery result set.
3. Clearing the query and every filter restores the creator-pinned mosaic and chronological feed exactly.

Locked posts use intentional negative space instead of automatic premium-media blur. A creator may explicitly publish a separate safe cover for a locked post.

## Production information architecture

### Patron routes

- `/` - canonical patron home and gallery.
- `/posts/[slug]` - canonical post detail.
- `/tiers` - unified membership catalog and Patreon continuity explanation.
- `/login` - site-account login and Patreon-link entry.
- `/account` - access sources, billing management, Patreon link, and migration guidance.
- `/privacy` - creator-approved privacy notice from the supplied template.
- `/terms` - creator-approved terms from the supplied template.
- `/content-policy` - creator-approved content policy from the supplied template.
- `/community` - optional route only when the creator chooses an internal handoff; otherwise the configured external community URL is used.

### Compatibility and preview routes

- `/p/[slug]` redirects permanently to `/posts/[slug]` while legacy generated links remain supported.
- `/preview` is an authenticated operator preview surface. It is not the production patron homepage and must be excluded from indexing.
- `/library`, `/structure`, `/style`, and every `/admin/**` route are operator surfaces.

### Patron chrome

The patron header contains:

- creator logo or avatar;
- creator display name linked to `/`;
- Tiers linked to `/tiers`;
- Account or Sign in, based on session state;
- optional Community link.

The patron footer contains creator identity, configured community link, and legal links. It contains no Hatch Console, Style, Library, admin, setup, Relay Studio, or operator links.

The default desktop navigation is one line and no more than 80px tall. Mobile uses a compact menu with visible focus and at least 44px touch targets.

## Homepage state machine

### Default state

The default state applies only when:

- the normalized search query is empty; and
- no media-type, tier, or mature-content filter differs from its default.

It renders:

1. creator identity and short introduction;
2. creator-pinned feature mosaic;
3. search and filter controls;
4. reverse-chronological recent posts;
5. optional community handoff;
6. legal footer.

The creator controls which eligible posts are pinned and their feature order. A post may appear in both the feature mosaic and recent feed. Feature placement never changes entitlement.

### Search state

The first non-empty query or any active filter enters search state. Search state:

- hides the feature mosaic and recent-feed composition;
- shows one full eligible-gallery result set;
- searches title, public tags, and description/body text the current account is authorized to read;
- supports image, video, audio, text, and download media-kind filters;
- supports tier and My tier filtering;
- supports the mature-content control when the creator's content requires it;
- preserves all server-side entitlement checks;
- keeps locked posts discoverable only through public metadata;
- never returns a premium body excerpt, attachment filename, media URL, object key, or search highlight to an unauthorized account.

For v1, matching is deterministic and reverse chronological. A later relevance algorithm may be introduced only with a versioned contract and stable test fixtures.

Filter changes update the result set without a full navigation. The URL query string records query and filter state so search results can be refreshed and shared without exposing patron identity or entitlement claims.

Clearing the query and all filters leaves search state and restores the original pinned order and recent-feed order. The implementation must not rebuild curation from search results.

### Search parity boundary

Preserve from the Relay gallery:

- title, tag, and description/body search;
- media-type filters;
- tier and My tier filters;
- mature-content control;
- clear-all behavior;
- accessible empty-results recovery.

Do not copy:

- collections;
- random walk;
- comments;
- favorites or saved items;
- creator-network discovery;
- Relay navigation or interaction telemetry that requires Relay.

## Gallery and card contract

### Feature mosaic

- Feature order is creator-published, not algorithmic.
- At least one feature may span additional columns on desktop.
- The mosaic collapses to one ordered column below 768px.
- A feature card shows only the fields allowed by its access and teaser state.

### Recent feed and search results

- Default sort is `published_at` descending, with stable post ID as the tie-breaker.
- Pagination is required. Infinite scroll may enhance pagination but cannot be the only navigation.
- Restoring a browser history entry restores query, filters, page, and scroll position where supported.
- Tags displayed on public or locked cards must be explicitly public metadata.

### Card fields

An unlocked card may show:

- approved cover or primary media;
- title;
- publish date;
- public tags;
- access label;
- optional short public description.

A locked card shows:

- title;
- publish date;
- required tier or member label;
- generic locked frame by default;
- optional creator-approved public cover;
- one context-appropriate action.

The card never fetches premium media while locked.

## Post content contract

Posts are the canonical visitor content unit. The future versioned post contract must include:

- stable post ID;
- stable slug plus redirect history;
- title;
- `body_html`, sanitized on write and render;
- `body_plain`, generated from the sanitized body for authorized search and accessibility fallback;
- publish timestamp and optional scheduled timestamp;
- public tag IDs;
- source-provider IDs and provenance;
- access policy;
- creator-published feature position;
- optional public-cover media reference;
- ordered media records;
- ordered embed records;
- ordered attachment records;
- optional per-post community CTA.

### Sanitized body

- Allow paragraphs, headings, lists, emphasis, block quotes, safe links, and approved structural markup.
- Remove scripts, event handlers, unsafe URLs, unapproved iframes, inline styles that escape the theme, and active content.
- External links disclose their destination and use safe target/rel behavior.
- The body model is sanitized HTML, not arbitrary raw HTML and not a page-builder block tree.

### Embeds

- The provider allowlist and sandbox policy are versioned.
- A third-party embed cannot be treated as secure premium delivery.
- Premium video/audio that must be access-controlled uses creator-owned private storage and the generated-site player.
- When an embed is unavailable, show a bounded fallback link or message without breaking the post.

### Media

- Images support ordered stacks and safe expanded viewing.
- Video supports an authenticated player, poster policy, keyboard controls, captions where supplied, and no unauthorized preload.
- Audio supports an authenticated player, keyboard controls, duration, and no unauthorized preload.
- Media dimensions or aspect ratio are reserved to prevent layout shift.
- Player controls and status are announced accessibly.

### Attachments

Each attachment records:

- attachment ID;
- post ID;
- safe display filename;
- MIME type;
- byte size;
- checksum;
- access policy;
- private object reference;
- optional creator-supplied description.

Downloads pass through the same account and entitlement evaluator as inline premium media. Responses use safe `Content-Disposition`, MIME handling, no-store or entitlement-safe caching, and auditable access without logging signed URLs.

## Locked content and teaser policy

The default locked state is minimal:

- title;
- date;
- member or tier requirement;
- generic branded locked frame;
- action selected from the access reason.

The creator may opt into a public cover per post. That cover:

- is a separate public object or explicitly public derivative;
- is never generated at request time from a premium original;
- is never accepted merely because its object key is difficult to guess;
- can be removed without changing the premium original;
- has independent alt text and crop approval.

Existing `blur`, `hard`, and `teaser` presentation dials affect frame treatment and copy only. They never authorize premium bytes. A blur treatment may blur only an explicitly public cover. No premium original is fetched for blur.

## Post-detail anatomy

An unlocked post renders in this order:

1. patron header;
2. primary media or media stack;
3. title, date, tags, and access/source status;
4. sanitized rich body;
5. inline video/audio or approved embeds in authored order;
6. attachment list;
7. optional community CTA;
8. next/previous post navigation;
9. legal footer.

A locked post renders:

1. patron header;
2. generic locked frame or explicit public cover;
3. title, date, and access requirement;
4. paywall action;
5. public community link when configured;
6. legal footer.

It does not render or request premium body, media, embed data, or attachment metadata.

## Tier catalog and conversion

`/tiers` is one catalog, not separate Patreon and independent storefronts.

Each tier card shows:

- public tier name;
- price and interval for independent billing;
- public benefit copy;
- access rank or coverage in patron language;
- Patreon continuity note where a mapped source tier exists;
- one primary action.

### Context-aware actions

- Anonymous existing Patreon patron: `Connect Patreon`.
- Anonymous new patron: `Choose this tier`, then account/login and independent checkout.
- Signed-in account with active Patreon access: `Already included`; no independent checkout prompt for the same effective access.
- Signed-in account with active independent subscription: `Manage billing`.
- Signed-in account with insufficient access: `Upgrade`.
- Dual-source account: show both active sources and never suggest duplicate purchase for equivalent access.
- Ineligible provider policy: block checkout and explain the available lawful path.

EH-051 provides checkout and portal primitives. EH-054 maps source tiers to products/prices and proves duplicate-billing safeguards. Neither slice may put provider-specific claims in the browser as entitlement truth.

## Login and account states

### Login

- Keep account login and Patreon connection conceptually distinct.
- Return paths are same-origin and allowlisted.
- Explain why an account is required before requesting a provider connection.
- Errors name the failed step and the safe recovery action.

### Account

The account page shows only server-resolved state:

- account identity and verification;
- effective access;
- Patreon link and freshness;
- independent subscription and portal action;
- manual grant and expiry when present;
- managed verification dependency and last service date when present;
- duplicate-source explanation;
- stale, expired, revoked, or provider-outage guidance;
- sign out.

## Creator controls and preview

Hatch Console must provide, by the responsible downstream slices:

- pin/unpin and order feature posts;
- set or remove a public cover;
- edit sanitized body, tags, embeds, media order, attachments, and access;
- preview Public, active Patreon, active independent subscriber, insufficient tier, expired/stale, dual-source, and admin states;
- preview default homepage and active search/filter state;
- publish one fixed visual scheme;
- edit public tier copy and inspect checkout destination;
- copy canonical patron-facing links.

Preview uses real sanitized creator content and the same access evaluator as production. Preview controls do not become production patron controls.

## Responsive behavior

Required review widths are 1440px and approximately 390px.

- Multi-column mosaic and search controls collapse explicitly below 768px.
- Patron navigation stays on one line at desktop and uses a compact mobile menu.
- No horizontal page overflow.
- Touch targets are at least 44px.
- Media reserves aspect ratio before load.
- Body text remains readable without zoom.
- Search/filter controls remain operable with the on-screen keyboard.
- Video, audio, and attachment controls do not overflow narrow viewports.

## Accessibility

- Provide a skip link and semantic landmarks.
- All routes and dialogs are keyboard operable with visible focus.
- Locked cards expose the access requirement and action without relying on color or imagery.
- Search announces result-count changes without moving focus unexpectedly.
- Filter buttons expose pressed state and clear labels.
- Media has authored alt text or an explicit decorative role.
- Video captions/transcripts and audio transcripts are shown when supplied.
- Paywall status changes use an appropriate live region.
- Motion respects `prefers-reduced-motion`.
- Text and controls meet WCAG AA contrast.

## SEO and indexing baseline

- `/`, public posts, public tier catalog, and approved legal routes may be indexed.
- `/preview`, `/admin/**`, account, login callbacks, API routes, and private media are not indexed.
- Every public post has canonical URL, title, description, Open Graph metadata, and safe public image only when explicitly available.
- Locked posts may be indexed by public title and public description only when the creator opts in. Premium body and attachment metadata never enter public metadata.
- Generate sitemap and robots rules from published public configuration.

## Required states and recovery

The visitor implementation must define and browser-test:

- loading gallery and post;
- empty creator library;
- no search results with clear-all action;
- post not found and legacy redirect;
- media unavailable;
- attachment unavailable;
- anonymous;
- signed in without entitlement;
- insufficient tier;
- stale Patreon observation;
- expired or revoked grant;
- active Patreon;
- active independent subscription;
- dual-source access;
- managed verification outage;
- billing checkout failure;
- restored billing access;
- creator-unpublished site.

Empty and failure states explain the next safe action. No celebratory or vague copy substitutes for verified state.

## Acceptance personas and network assertions

Browser acceptance covers:

1. public visitor;
2. signed-in account without paid access;
3. active Patreon patron;
4. active independent subscriber;
5. insufficient-tier patron;
6. expired or stale patron;
7. dual-source patron;
8. creator/admin preview.

For each persona, verify:

- `/`, `/posts/[slug]`, `/tiers`, `/login`, and `/account` behavior as applicable;
- default mosaic/feed and query/filter gallery transitions;
- exact restoration after clearing query and filters;
- expected primary and secondary actions;
- keyboard and mobile operation;
- loading, empty, degraded, and recovery state;
- no premium media, body, embed, attachment metadata, object key, or signed URL is requested or returned while unauthorized.

## Explicit exclusions

The v1 generated patron site does not include:

- comments;
- favorites or saved items;
- DMs;
- patron-to-patron community;
- Relay creator discovery;
- collections;
- random walk;
- engagement-ranked recommendations;
- arbitrary page building;
- custom scripts or raw CSS;
- generalized analytics.

Creators may link an external community such as Discord. That link does not make Relay or the generated site a community host.
