# PCB-04–06 backend implementation note

The accepted PCB-01–03 connectors are the starting state. Each ticket stays behind the current authenticated Conversation adapter and gets a separate review, confirm, read-back, and acceptance pass. The mock bench remains an isolated regression reference. No product mount, frontend or installed-extension verification, paid model call, actual-account write, production migration, deployment, restart, or publication belongs to these tickets.

## PCB-04: destination drafts and revisions

Use one `PostDistributionPlan` identified by its existing unique `conversationalGroupKey` for the selected source/export group. Add one `PostDistributionVariant` per separately confirmed X or DeviantArt destination. The existing `@@unique([planId, destination])` enforces one row per destination. The first confirmation creates the plan and first variant atomically; the second appends its variant to that same plan. The broad `createPostDistributionPlan` path cannot be used unchanged: `loadCanonicalCopy` accepts only `PostSource.RELAY`, although the real Library includes all active owned sources; its formatters may rewrite literal copy; and it archives an existing active plan before its transaction. Use the existing row builders in a narrow owned-source path with the approved copy supplied verbatim after destination validation.

Store bounded server-owned metadata under `PostDistributionPlan.assistantPlan.conversation_draft_v1`: pinned source post/version and effective-presentation digest, Previewizer receipt/media/hash, and each destination's revision number and ordered before/after entries keyed by review ID. Keep `assistantPlan.preview_media_id` and the variant's `platformFields.media_version = "preview"` for the existing media resolver. The current schema has neither a variant revision nor an edit-history record. This JSON journal is durable and can be append-only through the application service; it is not database-enforced immutable. An additional table is unnecessary if all managed writers are fenced and the focused PostgreSQL proof confirms atomic journal/row updates and restart read-back.

Review must show destination, exact X text or DeviantArt title/body/tags, selected JPEG, source/version, current revision, and field diff. At confirm, reload creator ownership, selected source/version/effective presentation, active ready JPEG and its PCB-03 provenance, plan identity, and current variant revision. Reject changed or expired reviews. Lock the plan and variant in one serializable transaction, compare the expected revision, write the literal copy and append its before/after entry, then store a receipt tied to the review ID. A successful exact retry returns that receipt. A later edit follows the same review/confirm path and clears an old approval. X and DeviantArt are independent; no source-post title/tag or original version is changed.

Fence these existing writers for plans with `conversationalGroupKey` set:

- `createPostDistributionPlan`, `reviseScheduledPostDistributionPlan`, and `getPostDistributionPlan` use broad active-plan lookup. The create path can archive a managed plan; revise can replace `assistantPlan` and draft copy. Legacy lookup should select non-managed plans, while Conversation reads by exact plan ID.
- `coach-checkpoint-service.ts` uses `findActivePlanRow` for propose/save/progress and can archive or replace `assistantPlan`. Its broad lookup must exclude managed plans.
- `schedule-rail-service.ts` `updateScheduleRailEventPostDetails` seeds variant title/body/text/tags. It must skip or reject a managed target before changing that variant or its source post.
- Legacy `patchDistributionVariant`, `approveDistributionVariant`, and `startDistributionHandoff` accept managed IDs today. Reject managed IDs with a use-Conversation conflict; the confirmed Conversation paths own copy revision, approval, and handoff. Metadata-only goal-cycle attribution/advice, reminder, and task-notification writes leave the managed journal and copy alone.

Focused tests: foreign/missing/replaced source or JPEG, changed effective presentation, exact literal copy and destination limits, X/DeviantArt independence, one plan/variant identity, stale and concurrent edit conflicts, append-only history, restart read-back, successful retry, and legacy-writer guards. Use the existing isolated PostgreSQL nonce database script and canonical migrations for transaction proof.

## PCB-05: one Rail cue per scheduled variant

Read the creator's posting-goal timezone through `getCreatorPostingGoalStatus` and `resolvePostingGoalTimezone`, as `getCreatorScheduleRail` does. Review the creator-local wall time, IANA zone, resolved UTC instant, destination, variant revision, and preview media. Use the existing local-time converter in `src/goal-cycle/planner/schedule-local.ts`; validate the round trip, including nonexistent or ambiguous daylight-saving times, before confirm. Confirm against the same owned active draft and expected revision.

In one locked transaction, set `PostDistributionVariant.scheduledFor` to the reviewed UTC instant and create one linked pending `PostbotTask` with `action: "post"`, matching `creatorId`, `postId`, `planId`, `variantId`, destination, and `suggestedTime`. The Rail reads task rows and prefers the variant schedule for due time. Record the confirmation's task ID and review ID in the managed plan metadata so an exact retry returns the same task; the lock and existing task check prevent a second task. Leave `remindMe` false unless a separately authorized reminder setting already applies. Do not create a second `CreatorScheduleEvent`: this task is the actual Rail authority. `createScheduledPostForRail` creates a new Relay post and draft, so it is not the connector for an existing selected artwork.

Prove one pending Rail task per destination after restart, correct UTC/local display and preview/source/variant links, concurrent confirm and exact retry, unchanged unrelated Rail entries, and no publication. The Rail may group tasks due in the same minute; inspect each destination child as well as the grouped card. Reschedule and cancellation remain outside PCB-05.

## PCB-06: owned manual handoff

Review the current approved destination revision, exact copy, pinned JPEG, and Rail cue, then require a separate handoff confirm. The existing `startDistributionHandoff` accepts drafts and always creates an attempt, so use a managed confirmed path that creates one `PostDistributionAttempt` per review ID under the plan lock and returns the prior receipt on replay. Keep a revision/attempt binding in managed plan metadata. A replay never sends another Open instruction; a new tab requires an explicit Open again action. Opening or filling leaves publication manual, and `fill_partial` remains partial.

The extension package GET already requires an active extension `SessionKind.extension` bearer grant and resolves the owning account. Keep that authority and recheck it on every package fetch, including after grant revocation. The managed package branch must additionally check attempt, creator, plan, destination, active draft, current approved revision, matching confirmed handoff, and the retained PCB-03 JPEG's provenance, readiness, storage key, and bytes/hash. Read copy and media IDs from server records. The existing `buildRelayCrossPostPackage` base accepts only `PostSource.RELAY`, so imported Library artwork needs a narrow managed package builder that emits the exact variant copy and one pinned JPEG without fallback to current source text or media. Keep the existing export media content URL and owner/grant checks on the bytes endpoint. A stale attempt or missing/changed JPEG must not yield a package. The current package GET unconditionally marks `package_fetched`; guard that update so stale/replayed requests cannot regress a completed attempt.

The development extension consumer should fetch the attempt package and JPEG through its grant, verify the media identity/hash, then open and fill only on an explicit Open instruction. It must not trust browser-supplied copy or media bytes. Focused backend and extension-unit tests cover foreign and revoked grants, stale copy/revision, missing JPEG, exact retry, one attempt, no duplicate tab command, and partial fill. Installed-extension execution stays at the separate product acceptance gate.
