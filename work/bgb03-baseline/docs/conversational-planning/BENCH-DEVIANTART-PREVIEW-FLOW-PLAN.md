# BDA-01: DeviantArt preview draft, schedule, and manual handoff

Status: accepted for the mock bench, 2026-10-20; Sol High planned, Luna High implemented, root reviewed; mock editor bench only. Build the DeviantArt counterpart of the accepted X BPX-01 → BPS-01 → BPH-01 flow in one bounded ticket. A creator selects a synthetic post, exports one Previewizer JPEG, reviews and confirms an unscheduled DeviantArt draft, reviews and confirms a Europe/London posting cue, then separately reviews and confirms an extension handoff. The creator reviews and publishes in DeviantArt. Keep the fixture original, selected/excluded IDs, active conversation choices, existing X drafts and their immutable receipts, and every confirmed DeviantArt payload unchanged by later turns or deselection.

## Product and data contract

The existing `platformFields` defaults (`mature: false`, `no_ai: false`, `created_using_ai: false`) remain in the variant; this mock handoff sends only title, `body_text`, tags, and the JPEG because the current DeviantArt extension package has no fields for those flags. The creator checks destination settings manually. There is no new description editor, generated rewrite, AI classification, or implied source-copy change. Review shows title, body, tags, field differences, actual pinned JPEG and source name; Confirm freezes the whole approved variant and source/export provenance. A changed title, description, tags, source or export requires another review and a separately identified draft. Preserve X's exact 280-character `postText` semantics.

Allow an explicit, quoted DeviantArt preview-first request in the existing conversation schema/instruction and deterministic quote validator. One active preparation destination is enough. A request for DeviantArt while X preparation is active must make a grounded destination switch or return clarification before changing state; it must never silently retain X and create an X draft. A valid switch retains selected/excluded IDs and recorded template/copy choice if still valid for DeviantArt, and leaves confirmed X drafts, pinned exports and receipts intact. If the recorded literal exceeds 200 characters, ask for a new title without mutating the prior goal. Ordinary conversation turns, selection changes and cancellation keep their existing invalidation rules for *unconfirmed* previews/reviews; confirmed drafts remain addressable from the same conversation after deselection or cancellation. Do not add a compound X+DeviantArt model workflow or a second fixture store.

The draft identity includes creator/session, destination, source version/fingerprint, source media, preview media and SHA-256, template/config, and the complete approved variant hash (title, body, tags and platform fields). Use the existing per-session 32 draft and 64 token-receipt limits, 1 MiB JPEG, 4 MiB/session, 32 MiB/API and two-hour idle expiry. The adapter's draft row builder and `scheduleDraft` currently hardcode X: make their destination/media binding/event title checks depend narrowly on the saved destination and its copy field. DeviantArt's event title equals the saved variant `title`; X remains `postText`. Keep an unscheduled draft until a separate date/time review and Confirm create exactly one pending, manual `make_post` event linked to the same plan/variant. Resolve future Europe/London time through the existing calendar resolver and display both local and UTC. No reminder, production Rail row, real Library attachment, mutation of the draft creation receipt, or scheduling from current selection text.

The handoff review reads the immutable creation receipt, schedule receipt, current adapter row and pinned export from the same API instance. Require matching owner/session, destination, plan/variant/event links, pending event and scheduled time, title/body/tags/variant hash, source/export provenance, preview-only media binding and SHA-256 of the live pinned JPEG. A distinct signed review token binds pending review, revision/generation, creator/session, draft identity, IDs, full copy/variant hash, source/export hashes, schedule and ten-minute expiry under the existing token limit. A newer turn, competing review, missing JPEG or altered fact stales the unconfirmed token. Confirm uses the session mutation guard and rechecks after awaits, then stores one immutable handoff receipt. Exact successful token retry returns the same receipt; a different stale token conflicts. Confirm does not alter the draft, event, copy, JPEG, selection or conversation goal. The first successful click may send one extension message; an existing receipt exposes an explicit **Open DeviantArt again** control, including after failed delivery. Neither fill nor tab open is publication evidence.

Add DeviantArt owner-scoped, development-only package/media reads through the existing schedule router and its `authenticateExtensionCreator` callback. Keep strict Bearer extension-grant authorization; cookies alone cannot read them. Prefer a destination-qualified handoff lookup or DA-specific route that cannot confuse an X ID; preserve the existing X URLs and payloads. Package contains exactly the confirmed `title`, `body_text`, `tags`, and one `image/jpeg` `bench_preview_*` media item with a narrow relative URL and SHA-256. `relay_post_id` is a mock transport handle. Revalidate receipt/event/provenance and pin on each GET; media returns at most 1 MiB with `private, no-store` and `nosniff`. No original-media fallback, bearer in URL, arbitrary URL fetch, production package write or cross-origin allowance.

The page sends only `{type:'RELAY_CROSS_POST', session_id, handoff_id, destination:'deviantart'}` from the explicit Confirm/Open button. Extend the strict mock branch in `cross-post-types`, keeping legacy post and schedule-event branches unchanged and the existing trusted-origin check in `background.ts`. The background fetches the exact package and single allowlisted JPEG with its grant, bounds bytes and verifies MIME/SHA-256 **before** opening the DeviantArt tab. Build one JSON-safe, short-lived, tab-bound packet containing frozen title/body/tags and verified JPEG bytes; inject it into that tab's isolated world before the existing DA fill script. Consume/delete it once, before any long editor wait. No `pending_cross_post` storage or global packet, even when two handoffs overlap; no grant or bytes in the page DOM/storage.
