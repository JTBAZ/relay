One local `/editor-bench` page with a small Lab2-style gallery grid, mode switch (**Curation** / **Mock posting**), selection, chat composer, example prompts, editable strict structured-intent JSON, and a spacious result panel. Three explicit states are shown beside every turn: **Example replay** (preauthored intent paired to that exact example), **Edited replay** (user-edited strict intent), or **Model interpretation** (only if a real configured provider was invoked). Free text without a configured provider must explain that interpretation is unavailable and offer the editable replay; it must not choose a canned response by keywords, semantic similarity, or prompt matching. Example buttons may load their paired request and structured intent but changing the request detaches the pairing.

The curation result shows the selected fixture posts, exact proposed actions, before/after names/collection membership/order, preserved exceptions, unresolved or rejected items, and the factual cart preview. The mock-posting result shows source, draft, Previewizer dependency, separate Patreon/X/DeviantArt handoffs, blocked destinations, and publication-relative follow-ups as a readable graph/list. “Prepare,” “post,” and “apply” controls must not call production authorities; any local apply/undo only updates per-tab fixture state and is labelled simulation. A compiler refusal or clarification stays visible as such, with no fabricated plan. No vision claim, real post, scheduled reminder, or successful external publication is implied.

All fixtures use synthetic creator/post/media/template IDs and metadata. The request carries at most the existing interpreter limits; the server rebuilds trusted fixture context/evidence and rejects client-authored state or authority IDs. Response includes a finite mode/provenance discriminator, interpreted object, validation/compile outcome, human-readable before/after, and diagnostic code. No global process session, persisted DB row, cross-browser shared state, production gallery fetch, or destination API call. A local dev-only API rejects production deployment and enforces bounded JSON; browser selection and edited intent are untrusted inputs. The demo is reachable through the direct route only, with production feature flags/default routing unchanged.

Freeze the request/response seam before UI work:

```ts
type BenchRequest = {
  mode: "curation" | "mock_posting";
  selectedPostIds: string[]; selectedMediaIds: string[];
  replay:
    | { kind: "example"; exampleId: string }
    | { kind: "edited"; latestRequest: string; structuredIntent: unknown }
    | { kind: "free_text"; latestRequest: string };
};
type BenchResponse = {
  mode: BenchRequest["mode"];
  provenance: "example_replay" | "edited_replay" | "model_interpretation" | "none";
  status: "proposal" | "unchanged" | "clarification" | "limitation" | "rejected" | "unavailable";
  interpreted: unknown | null; result: unknown | null;
  beforeAfter: { label: string; before: string | null; after: string | null }[];
  diagnostics: string[]; message?: string;
  runtime?: { enabled: boolean; model: string | null; reasoningEffort: "none" | null;
    remainingUsd: number | null; reason: string | null };
};
```

The server derives provenance; the client cannot assert it. An example ID resolves an exact server-owned request, intent and selection. If the creator edits the request or JSON, send `edited`. `free_text` returns `unavailable` when the opt-in bench runtime is not configured; otherwise the existing interpreter returns a genuinely model-derived result. No example is auto-selected.
