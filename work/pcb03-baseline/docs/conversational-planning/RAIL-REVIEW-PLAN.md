## Artist experience and state transitions

1. **Select and ask.** The rail composition section offers **Plan selected art** and **Saved plans**. Selection summary shows the actual selected count and available Library labels. Empty selection asks the artist to select art; over three media or four posts asks them to narrow. No first-N truncation. A Library attached image can identify an existing source post; it cannot be attached to a new draft through an invented copy adapter. The server resolves authority and returns clarification/limitation for unsupported source use. CP-10 does not add a staging picker; another accepted entry can later supply eligible READY staged IDs through the same bounded props.
2. **Compose.** A single responsive dialog shows the frozen selection for this submission, a 4,000-character request input and optional saved-template chooser. Explain “Uses titles, file details and saved metadata; does not inspect the artwork.” Displayed authenticated artwork thumbnails, if reused from Library, are browser presentation only: no URLs, bytes, image descriptions, `input_image`, loaded gallery rows, filter state or thumbnail payload enter the planning request. Do not prefill a fabricated series part, title, engagement action, source reuse or time. The artist's text is sent exactly after nonblank validation; count/limit without silent trimming.
3. **Review saved composition.** A stored result opens the same plan ID and revision, then GETs current detail/preview. Show source, complete titles, copy provenance, template identity, destination groups, dependency labels, notes, enabled state, absolute local date/time + IANA zone + UTC instant, and relative day+1/day+2 action/destination/anchor/local-time rules. Render `part_substitution` by its declared prefix + part + suffix with provenance; literal `X` stays literal. All saved steps, groups, unresolved request quotes and clarification scope are visible; long text can expand, never truncate the value being approved. Topological display and grouping are presentation only; no drag-to-reorder graph mutation. Use stable node IDs, not position, for edits and focus.
4. **Clarify.** An interpreter/compiler `clarification` may have no saved plan. Display its actual question; an optional clarification preview is explicitly “Not saved” and has no executable rows or confirm control. Preserve the latest unsent request in memory so the artist can submit a complete corrected request with the original intended scope and a new mutation key. The API has no `answers` array, persisted chat or automatic conversational memory. For a saved partial proposal, show each blocking slot beside affected nodes, retain clear independent work, and send explicit AI revision text or supported manual patches. The planned UI disables whole-plan confirmation while preview reports clarification/unresolved blockers; independently clear rows are not a partial-approval promise in this UI. Actual service reviewWrite currently validates fresh context but has no separate all-blockers readiness check. Do not claim that UI rule is already enforced server-side; preparation must independently block affected nodes and dependents under its existing contract. Any stronger approval policy needs a separately reviewed bounded correction within the consent milestone.
5. **Revise while proposed.** Manual title/note/enabled/time edits are explicit Save operations; AI revision can target GET-provided revision handles. For more than eight editable steps, require the artist to choose up to eight exact handles; do not choose a hidden subset. Manual edits use step IDs, title `{mode:"literal",value,origin:"creator"}`, exact note (including empty/whitespace) or explicit null, boolean enabled and valid TimeSpec/null. Only changed fields enter a nonempty patch (max128; one entry per step/field). Distribution title patch is mapped by the server to its coupled copy title; UI does not independently patch `copy_title`. No destination/source/template/social-action manual field is invented. Repair instructions may require a fully specified AI request; unsupported replacements remain an honest limitation. Source selection is retained for revisions, not silently replaced by subsequent Gallery selection.
6. **Consent.** A dedicated summary says what can be prepared now and what waits on later adapters. **Confirm plan** is an explicit click, separate from Ask, Save changes, close and opening a detail. Proposed review with no preview blockers is necessary, not sufficient proof of authority availability. Confirm is disabled when preparation capability is unavailable, writes are locked, a request is in flight or reviewed detail/preview revisions disagree. The normal v1 flow calls `/confirm` directly, combining approval with preparation; a separate `/approve` button is unnecessary. It never says Publish, Posted or Scheduled merely because it saved a plan or received pointers.
7. **Preparation and retry.** After any confirm response, including authority-gap/timeout/unknown outcome, GET current detail and preview on an explicit recovery/read path. Show linked source post/draft and attention event separately; show supported live rail event data only after actual rail reload. `AUTHORITY_GAP` can follow partial committed preparation, so do not clear the proposal, create another plan, replace a source or use a new approval key. Keep the exact pending confirm body in controller memory for an explicit same-tab replay; after reload, **Continue preparing** uses accepted CP-08g with the freshly read approved revision. Preview/template render, teaser distribution/handoff and social actions remain “Waiting for preview integration”, “Waiting for destination handoff”, or “Waiting for qualified publication” as appropriate to the declared dependency; these describe composition constraints, not invented live execution states.

Concrete first journey: select attached art on an owned existing Relay post; request explicitly reusing that post for creator handoff to Patreon, an exact literal title, and “20 October 2026 at 18:00 Europe/London”. ## In-memory mutation replay and approved-revision recovery

`service.confirm` calls `reviewWrite(...,"approve")` before its adapter. For an already approved plan, a new key and even the latest approved base revision cannot perform a new approval: review must be `proposed`. An approval HTTP replay requires the **original** key and **original proposed** base revision. `recordedRevision` is the recorded approval revision, while `current` can be newer; never approve a stale returned snapshot or equate the two unconditionally.

Keep the exact pending `/confirm` body and its original proposed base revision in controller memory before sending. An explicit same-tab retry reuses that exact body after a fresh authenticated read; it never invents a replacement approval key. Creator/session change clears the body and ignores old responses. After reload or on another device, a successfully read `approved_for_preparation` plan can offer **Continue preparing**, which submits only its exact displayed approved revision through accepted CP-08g. There is no localStorage receipt or replay utility in this delivery. A failed GET cannot render an old graph or enable preparation; source drift can make GET or resume fail honestly with Reload. `useStudioSession` exposes `ready`, `creatorId` and `studioIdFromSession`, not `accountId`; backend cookie authentication remains final authority.

Reopen a saved plan via read-only `?conversational_plan_id=<id>` or explicit list selection in CP-10e; consume only that query key and leave automation parameters intact. Opening, GET and list never call confirm or resume. A cancelled or replaced revision disables an obsolete in-memory confirm body. Approved staged-source publication can change canonical relationships and remains a separately reviewed source-handoff gap.

Create and revise also need stable per-attempt keys retained while an outcome is uncertain; edits to the body create a new deliberate attempt/key. Preserve exact pending request bodies in controller memory for explicit same-tab retry. Do not persist full request text/patches by default. Reload after an uncertain create can discover saved plans through GET list but cannot promise exactly-once create recovery after the pending key/body were lost; never auto-resubmit it. This bounded limitation must be visible in acceptance, not solved by guessing a matching title.
