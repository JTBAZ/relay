
The schema has exact keys and disjoint `kind` values from the existing single manual event and CP request. A common title or time is repeated in each event, so the model need not invent destination-specific copy. Destinations must be distinct. The existing selector must resolve exactly one authorized fixture post and one to three distinct associated media IDs; every event shares that source. `source_ref` must match the resolved source. A selected-art reference preserves current selection; a named or contextual source uses the existing selector, including BCS-01 criteria. A request with two sources, duplicate destinations, more than three events or an unresolved source asks for clarification. There is still **one** `gpt-5.6-luna` / `none` provider call, with no automatic repair, fallback or additional paid worker call.

The server maps every item with the existing single-event constraints: nonblank trimmed title of at most 200 characters copied literally from the latest request, nonblank exact `time_text` substring, valid complete date/weekday fields, Europe/London and a future UTC instant from `resolveAbsoluteTime` using one fresh server clock. Refactor the pure `manual-posting-event.ts` mapping so the batch reuses its owned-fixture, title and time checks; the batch Patreon item is **direct manual-event data**, never a fabricated CP `primary_draft`. All items must map successfully before any proposal or review is returned. The server owns `event_type:'make_post'`, `target_mode:'new_post'`, `post_id:null`, `external_url:null`, `create_relay_draft:false`, `remind_me:false` and a sample-source note for each item. The batch response is `result.manualPostingEvents: ManualPostingProposal[]`, not a compiled graph. Update the existing single-event prompt's “multiple destinations clarify” sentence so it explicitly allows **only** this two-to-three-destination direct manual batch; single Patreon still uses its compiler and single X/DeviantArt still use their direct intent. The model must preserve every requested supported destination or clarify; requests for drafts, teasers, templates, exports, publication, follow-ups, recurring reminders or other unsupported actions cannot be silently reduced to manual cues. Do not add a platform-name keyword/coverage parser: it would misread exclusions and context. A strict shape cannot by itself prove full natural-language coverage, so record any observed omission as a model failure and check the exact destination set in a bounded live request.

## Group review, individual confirmation

Keep `POST /api/v1/editor-bench/schedule/review` and its exact request body (`latestRequest`, `structuredIntent`, `selectedPostIds`, `selectedMediaIds`). `reviewBenchSchedule` returns either the existing single `{kind:'review', review, reviewKind}` or a new `{kind:'batch_review', reviews}`; refusal returns **no** review items. Revalidate the whole untrusted batch against fresh server-owned fixtures and one clock before token creation. The route then returns one authenticated, read-only grouped response:

```ts
type BatchReviewResponse = {
  reviewKind: 'manual_batch';
  items: Array<{
    destination: 'patreon' | 'x' | 'deviantart';
    review: ScheduleReview;
    reviewToken: string;
    expiresAt: string;
  }>;
};
```

The existing single response `{reviewKind, review, reviewToken, expiresAt}` is unchanged. Sort batch items in fixed Patreon/X/DeviantArt order for stable display. Sign **each** existing canonical `ScheduleReviewPayload` separately with the current creator binding, expiry and HMAC; mint tokens only after all reviews pass. `POST /confirm` continues to accept exactly `{reviewToken}` and writes one event per explicit button press. Its deterministic creator-plus-payload ID already includes destination; its collision read compares destination and all other owned facts. No batch-confirm endpoint, Confirm all button, transaction across destinations or hidden confirm loop. A creator may confirm one event and leave the others pending. An expired token requires a fresh group review; identical canonical payloads still deduplicate safely after a lost response.

The page shows one grouped review with a row per destination, literal title, local due time and the no-attachment/manual-publishing notice. Each row has its own `Confirm event`, saved receipt and error/retry state; a single global busy lock is acceptable. A failure on X must not hide a saved Patreon receipt or confirm DeviantArt automatically. `Review again` refreshes pending/expired tokens without clearing a saved receipt **only when that row's complete canonical `createPayload` is unchanged**; changed request, selector, source, title, time, destination or payload clears the affected row and stale token through the existing generation invalidation. A saved row remains visibly saved and is not confirmed again by the UI. Keep the existing single card behavior, schedule link and development-only gate.
