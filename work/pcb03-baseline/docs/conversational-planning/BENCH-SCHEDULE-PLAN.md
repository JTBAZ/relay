## Decision and existing seams

Use the existing manual Schedule Rail authority for **one standalone Patreon `make_post` event**. The creator asks in `/editor-bench` for a dated, timed posting action based on one synthetic Library item; the existing `gpt-5.6-luna` / `none` free-text bench call interprets it under the current development budget, and the fixture compiler builds its mock posting graph. A separate authenticated, development-only review request recompiles the exact interpreted intent against server-owned fixtures without another model call. The creator then explicitly confirms the returned canonical review. Confirmation persists one manual event through `createCreatorScheduleEvent`, with `post_id: null`, `external_url: null`, `create_relay_draft` absent and `remind_me: false`. The event title/date/destination appear on the real Schedule Rail; no media is attached and no draft, Previewizer result, handoff, external publication or follow-up is created.

This route is narrower than the CP lifecycle. The bench's `bench_*` post/media IDs are synthetic and must never be passed to `Post`, `AutopostDraft`, `CreatorScheduleEvent.postId`, or any owned-media lookup. CP-08/09 preparation requires real owned media or a real post and its plan tables and `conversational_step_key` column belong to the CP migration, which has not been applied to the ordinary database. The existing manual event service already supports an unlinked `make_post`, performs Studio Core gating and validates real linked posts when one is supplied. Its public POST route authenticates the creator, but its create path currently has no idempotency key. The new bench route should reuse its create validation, without changing the ordinary manual event contract or introducing a general plan/session engine.

## Frozen first-slice behavior

- **Eligible proposal:** `mock_posting` only; one selected, owned fixture post and **one to three distinct media IDs associated with that post**. One strictly validated interpreted `primary_draft` request targets Patreon with `prepare_for_creator_handoff` and a literal title. Its `source_ref` may be `{ mode: "selection", id: null }` or `{ mode: "post_id", id: selectedPostId }` exactly. Its time intent may be `absolute_local` or a qualified `weekday`; the existing compiler, using the fresh request clock and confirmed `Europe/London` timezone, must resolve it to a **future absolute** date/time. The offline compiler must return a plan with no clarification or unresolved request and exactly its normal three enabled steps: timed `prepare_post_draft`, dependent untimed Patreon `prepare_distribution`, then dependent untimed Patreon `publish_handoff`, with one matching distribution group. The canonical title must be nonempty and at most 200 characters **before** review; reject a title that the event service would silently trim or truncate. Do not add a second time parser. The review explicitly identifies the **single** manual event that confirmation will create and labels the two companion steps as unexecuted graph context. Reject requests for teasers, multiple destinations, follow-ups, ambiguous sources, missing dates/times/timezones, disabled primary steps or extra requested actions; never silently persist only part of a larger request. Do not turn a compiler draft or source into a real post.
- **Review:** browser sends the latest request, strict interpreted intent and selected fixture IDs via the existing authenticated `relayFetch`/`relayRequest` cookie path to a new backend review POST. The backend treats all fields as untrusted, requires `NODE_ENV=development` explicitly (unset is closed), authenticated creator with `readonlySession: true`, and body bounds. It runs `runPostingBench` in edited replay with a fresh server clock, then derives the event fields from the validated graph. Return an explicit review card (`fixture source title`, Patreon, exact title, local and UTC due time, no attached media, no reminder, one event only) and an opaque integrity-protected token bound to the authenticated creator and canonical event payload. No database write or model call occurs here, including expired-session cleanup. A changed request, selection, interpreted intent or review value invalidates the visible card and requires another review.
- **Confirm:** a separate backend POST accepts the review token only after an explicit button press. Verify its signature, expiry, creator binding and exact canonical payload; do not accept client-authored event fields or a creator ID. Derive a stable event ID from creator plus canonical reviewed proposal so a repeated confirm, including after a lost response and fresh review of the identical proposal, addresses the same row. Add the smallest internal trusted-ID seam to `createCreatorScheduleEvent`; keep its Core gate and field validation. On ID collision, reread by `(id, creatorId)` and compare the complete owned event facts (type, destination, title, note, due time, null post/URL, reminder setting); return `reused` only on an exact match, otherwise conflict. Handle concurrent unique-key races the same way. A missing/expired token asks for review again; never guess that a previous write succeeded. A random in-memory signing secret per server process is sufficient for this local development bench; restart invalidates the token, while stable event ID from the reviewed content keeps an identical re-review retry safe. Use constant-time signature comparison and a short token lifetime.
- **Read-only semantics:** bench catalog GET and chat/proposal/review POSTs make no database write; only explicit confirm writes. Keep the bench development-only on both web and backend routes, including production 404. No production default model/flag change. The review and receipt distinguish a real persisted rail event from synthetic source art, and link to the real rail event if its existing UI route supports it. No publish action is implied.

## Parked work and limits

CP plan persistence and real Library source attachment, grouped rail UI, draft and Previewizer preparation, X/DeviantArt handoffs, publication-qualified day+1/day+2 actions, production rollout, ordinary DB migration, and full frontend QA remain separate. A standalone manual event carries only title, note, destination and due time; its note may say the source was a sample fixture, but it must not encode a fake `post_id` or claim that art is attached. Exact same creator/proposal facts deduplicate by design; creating a second intentionally identical event requires a future explicit workflow decision. A server restart invalidates an unconfirmed review token, in which case the creator reviews again; the canonical event ID ensures identical re-review does not duplicate a confirmed row. If an ordinary database compatibility check exposes another implicit Prisma read of a CP-only column, BS-02 should narrowly avoid that field or report the concrete dependency before claiming this slice works on the ordinary DB.
