## Repository surface

Implement a typed `ConversationalPlanRepository` over an injected Prisma client in `src/conversational-planning/persistence.ts`. All methods receive an **authenticated server-side creator ID**; CP-08 will enforce the account/creator/Tenant route gate. No method accepts a model-supplied creator ID or arbitrary Prisma `where`. Suggested result union is `{kind:"ok", current: PlanSnapshot, recordedRevision: number, pointers: CheckedPointer[]}`, `{kind:"not_found"}`, `{kind:"creator_not_provisioned"}`, `{kind:"idempotency_conflict"}`, `{kind:"revision_conflict", current: PlanSnapshot}`, or `{kind:"invalid_snapshot"|"stale_source"|"authority_gap", code:string}`. A replay's `recordedRevision` may be older than `current.revision`; return both distinctly. Do not return raw unvalidated JSON or pointer rows as an `ok` result.

The public method shape should be concrete, for example:

```ts
type TargetHandleRef = { handle: string }; // server-issued alias echoed by the client; never a binding map
type Command =
  | { operation: "create"; latestRequest: string; selectedPostIds: readonly string[]; selectedMediaIds: readonly string[]; selectedTemplateIds?: readonly string[] }
  | { operation: "revise_ai"; planId: string; baseRevision: number; latestRequest: string; selectedPostIds: readonly string[]; selectedMediaIds: readonly string[]; selectedTemplateIds?: readonly string[]; targetHandleRefs?: readonly TargetHandleRef[] }
  | { operation: "revise_manual"; planId: string; baseRevision: number; patch: readonly ManualFieldPatch[] }
  | { operation: "approve"; planId: string; baseRevision: number }
  | { operation: "cancel"; planId: string; baseRevision: number };
type Mutation = { creatorId: string; clientMutationKey: string; command: Command };
interface ConversationalPlanRepository {
  lookupReplay(input: Mutation): Promise<ReplayResult>;
  create(input: Mutation & { command: Extract<Command, {operation:"create"}>; snapshot: PlanSnapshot }): Promise<WriteResult>;
  get(creatorId: string, planId: string): Promise<ReadResult>;
  listCurrent(creatorId: string, page: {limit: number; cursor?: string}): Promise<ListResult>;
  revise(input: Mutation & { command: Extract<Command, {operation:"revise_ai"|"revise_manual"}>; candidate: PlanSnapshot }): Promise<WriteResult>;
  approve(input: Mutation & { command: Extract<Command, {operation:"approve"}> }): Promise<WriteResult>;
  cancel(input: Mutation & { command: Extract<Command, {operation:"cancel"}> }): Promise<WriteResult>;
  listCheckedPointers(creatorId: string, planId: string): Promise<PointerReadResult>;
  putCheckedPointer(creatorId: string, planId: string, pointer: StepPointer): Promise<PointerWriteResult>;
}
```

`ManualFieldPatch`, pagination cursor, and result unions should be closed bounded types defined in this file, not `unknown`/free-form object inputs. Construct the repository with a **server-only creator-scoped context loader** that takes `(authenticatedCreatorId, candidateSnapshot)` and returns a fresh `TrustedPlanContext` plus source fingerprint; CP-07b mocks this seam and CP-08 later supplies production lookup. This loader is for contract validation only. It cannot assert pointer ownership, which the repository checks through its own fixed Prisma queries.

`targetHandleRefs`, when present, contains at most 32 distinct `{handle}` objects with no other keys; each handle is a nonempty string of at most 100 characters, matching CP-05's handle bound. The client may echo only server-issued aliases; resolve each against the server-held `(creatorId,planId,baseRevision,stepId)` binding before new compilation. Never accept a client binding map or raw step IDs as authority. Validate the closed command schema, reject unknown keys, and enforce explicit request, selection-ID/count and serialized-payload bounds before hashing; the TypeScript shape alone is insufficient. Hash the validated handle-reference array exactly, preserving order; omitted and empty references normalize to the same empty array. Do not add arbitrary request JSON. Structured clarification-answer fields are deferred: adding them requires a separately reviewed closed, bounded schema and inclusion of every accepted answer in the precompiler hash.

`selectedTemplateIds` is optional only on `create`/`revise_ai`: at most three distinct nonempty trimmed strings, each at most 160 characters, with no arbitrary row/config JSON. CP-08 loads exactly the selected creator-owned rows and requires the exact count. Omitted/empty means no explicit selection; automatic catalog offering is allowed only when the catalog has at most three templates. Otherwise return `Choose up to three saved templates` through the existing template UI, never delete saved templates or silently select the first three. AI revision may merge the selected IDs with retained preview-template references relevant to its edit scope only within the three-template prompt bound; otherwise narrow scope. Every retained preview config is still validated by fresh server context, independently of prompt selection. Manual revise/approve/cancel command shapes remain unchanged.

| Method | Input and output rule |
|---|---|
| `lookupReplay(creatorId, clientMutationKey, requestIdentity)` | Read both creator-scoped revision key and create key before compiler work. If absent, return `new`; if the recorded request hash matches, return recorded revision plus freshly read current plan and checked pointers; otherwise `idempotency_conflict`. A key reused across create/revise/approve/cancel is a conflict even if its text is similar. |
| `create(...)` | Require a provisioned `Tenant.relayCreatorId`, `revision=0`, `review="proposed"`, matching creator/source/ID/time fields, and both contract validators against fresh server context. In one transaction insert current plan and immutable revision 0 with the same client key/hash. Recheck key inside the transaction or after a unique race; return replay only for the same operation/hash. No authority pointer is created. |
| `get(creatorId, planId)` / `listCurrent(creatorId, limit, cursor?)` | Query by creator and bounded plan ID/cursor, validate current row projection and snapshot, then run `validatePlanWithContext` using freshly creator-scoped source/template/connection/entitlement context. Fail closed on corrupt/stale data; never silently repair JSON. List returns validated current snapshots in deterministic `(updatedAt DESC,id DESC)` order with bounded page size, and no revision history or raw authority state. |
| `revise(...)` | Replay check first. Require candidate same plan/source/creator/created time, `revision=baseRevision+1`, unchanged review (`proposed` for CP-06 pure revisions), and validated current/source context. CAS current row and insert exactly one immutable revision in one transaction. No hidden merge or retry against a newer revision. |
| `approve(...)` / `cancel(...)` | Replay check first; accept a server review command and base revision, never a model-supplied review field. Revalidate current snapshot/context, advance one revision by CAS plus immutable revision insert, changing only `review` and server `updated_at`. `approve` transitions `proposed → approved_for_preparation`; `cancel` transitions `proposed|approved_for_preparation → cancelled` under reviewed authority constraints. Do not claim preparation, deletion, or publication. Repeated *same key/hash* replays; a new key against a terminal or stale state returns an explicit conflict. |
| `listCheckedPointers(creatorId, planId)` / `putCheckedPointer(creatorId, planId, pointer)` | Optional second slice below. Return only pointers whose live authority row and parent links pass narrow creator-scoped checks. Insertion is idempotent only for the exact same `(node,slot,kind,authorityId)`; a different authority in an occupied slot conflicts. No replacement of `current_attempt` in CP-07b. |

The context loader means server-assembled, fresh `TrustedPlanContext`; it is never request JSON. Prefer one repository-private loader shared with CP-06's `TrustedLookup` adapter later, not a client-supplied assertion of owned IDs. Every write and read checks `validatePlanShape`, `validatePlanWithContext`, and equality of `plan.id/creatorId/revision/review/sourceRef/schemaVersion` to the embedded snapshot. Also validate immutable revision JSON when returning replay/history evidence. A context failure returns a scoped error and no `ok` snapshot; it does not rewrite the source fingerprint or template snapshot.

## Replay and transaction rules

Use SHA-256 of versioned, canonical JSON with recursively sorted object keys, order-preserving action/patch arrays, and exact title/quote bytes. The **precompiler request identity** is `v`, authenticated `creatorId`, operation, `planId` and `baseRevision` when present, plus the normalized creator command: for create, exact latest request and bounded selected post/media IDs plus any nonempty `selectedTemplateIds`; for AI revise, exact latest request, selections including any nonempty `selectedTemplateIds`, and the bounded client-supplied `targetHandleRefs` above; for a manual edit, the exact validated sparse field patch, including explicit clears; for approve/cancel, the exact review command. Exclude newly generated plan/node IDs, timestamps, the server-held handle binding map, fresh source fingerprint, provider output, and current authority state, so a retry after those change returns its recorded result. The existing input `planId` and echoed server-issued handle references remain hash inputs. Normalize post/media selection IDs as sets only if selection order has no contract meaning; preserve the exact accepted template-selection array order and textual copy. Bound key length and payload before hash. Never log command text, hashes with secrets, or full URLs.

**V1 hash compatibility:** normalize omitted/empty template selection to identical no-selection behavior by **omitting `selectedTemplateIds` from canonical command JSON** in both cases. Do not add `selectedTemplateIds:[]` to old command identities or change the existing `targetHandleRefs` normalization. Nonempty template selections are canonical hash inputs, so reusing a key with different/nonempty selections conflicts. Old clients can continue omitting the optional field, and stored pre-amendment v1 digests remain valid without rewriting immutable revisions. The focused follow-up tests use an old pre-change digest fixture to prove omitted/empty equivalence and changed/nonempty selection conflict, plus duplicate/count/ID-bound rejection. Luna CP-07b1 owns this narrow persistence/test update while CP-08a2 owns the disjoint context implementation; no DDL, paid call, repricing or new budget ledger is needed.

Root ratified this distinction, now reflected in PERSISTENCE-PLAN: an AI revision cannot be replayed safely by rerunning an interpreter/merge after its base revision has become stale. Store the hash of the stable creator request envelope **before compilation** for AI revisions; use the exact validated patch for manual revisions. `lookupReplay` searches `CreatorConversationalPlanRevision` by `(creatorId,clientMutationKey)` first and also the plan's `(creatorId,clientCreateKey)` as a consistency check. The revision-0 row records the create hash. A same-key different-hash or different-operation collision fails even if the current plan has advanced. For a same-key match, read the immutable recorded revision and current plan separately, and recheck pointers against live authority rows. A unique-key race goes through a bounded re-read of the winner; do not rerun compilation or retry the losing CAS with a new base. Replay lookup precedes current handle-map resolution, so an accepted command can replay after its original handles cease to be current.

For a new mutation, verify tenant provisioning and candidate/context before the transaction. In the transaction, recheck the key, conditionally `updateMany` the current plan on `(id,creatorId,revision=baseRevision)`, and insert revision `baseRevision+1` with the same snapshot/hash/key. A zero-row update returns `revision_conflict` after reading the current valid snapshot. The transaction rolls back on unique/serialization failure; a bounded re-read distinguishes same-key replay from conflict. For create, the plan and revision 0 insert commit together. Never update/delete a revision row. The database's unique `(planId,revision)`, `(creatorId,clientMutationKey)`, and `(creatorId,clientCreateKey)` arbitrate races; repository checks provide clear errors. CP-08 must recompute source fingerprint and revalidate immediately before submitting a candidate; CP-07b cannot atomically lock every media/template/connection source row with a plan CAS. If source changes between that check and commit, CP-08/09 must detect drift before preparation; do not present CP-07b as solving that concurrency boundary.

## Narrow pointer resolver, second slice

Keep the authority resolver **private to the repository**, with an exhaustive `switch(slot)` and no public callback of the form `isOwned(id)` or `resolve(kind,id)`. Query exact existing Prisma models by `id` **and** `creatorId` where present, then compare real parent fields and the candidate plan node. The CP-07a slot/kind CHECK and `validateStepPointer` are necessary shape guards, not ownership proofs. Both `put` and `list` re-read the live authority; a stale pointer is an `authority_gap`, not a status copied into the plan.

| Slot / owner node | Required live linkage before CP-07b accepts it |
|---|---|
| `draft` / `prepare_post_draft` step | `AutopostDraft.id`, `creatorId`, `conversationalStepKey === plan:{planId}:step:{stepId}`. |
| `attention_event` / `prepare_post_draft` step; `engagement_event` / matching `reply_block` or `engagement_check` step | `CreatorScheduleEvent.id`, `creatorId`, `conversationalStepKey === plan:{planId}:step:{stepId}`; if `postId` is set, it must be the plan's creator-owned source or verified relay-post pointer. Compare real `eventType` and `destination` against the exact CP-09 action mapping once defined; until then return `authority_gap`, since a key alone does not prove an event has the right purpose. No event status is copied. |
| `relay_post` / source step | `Post.id`, `creatorId`; either exactly `snapshot.source.post_id` for an existing source, or exactly the `publishedPostId` of the source step's checked draft. No arbitrary creator-owned post may be attached. |
| `distribution_plan` / `DistributionGroup.group_id` | `PostDistributionPlan.id`, `creatorId`, `conversationalGroupKey === plan:{planId}:group:{groupId}`, and `postId` equal to the checked source/relay post; optional `sourceDraftId` must match the checked draft when present. |
| `variant` / `prepare_distribution` step | `PostDistributionVariant.id`, `creatorId`, `planId` equal to the checked group distribution-plan authority ID, `postId` equal to its `PostDistributionPlan.postId`, and `destination` equal to the step destination. The step must appear once in that group's `destination_step_ids`; existing `(planId,destination)` uniqueness remains authoritative. |
| `current_attempt` / `publish_handoff` step | `PostDistributionAttempt.id`, `creatorId`, `variantId` equal to the checked same-destination variant pointer, and `postId`/`destination` equal to that variant. No replacement or new attempt creation here. |
| `preview_media` / `prepare_preview` step | `MediaAsset.id`, `creatorId`, `upstreamStatus=active`, and `currentStorageKey` or `currentUpstreamUrl` populated prove ownership/export readiness, **but not** which plan/template produced it. Until CP-09 supplies an authoritative source/template/export relation, return `authority_gap` for insertion rather than accepting any owned media ID. Existing pointer reads also fail closed if provenance cannot be verified. |

Never update `AutopostDraft`, `CreatorScheduleEvent`, `PostDistributionPlan`, `PostDistributionVariant`, `PostDistributionAttempt`, `Post`, or `MediaAsset` in CP-07b. The nullable correlation fields are written by CP-09's authority services, not by this pointer repository. Pointer insertion validates the plan current snapshot and node, checks the slot owner, checks the authority, then inserts under `(planId,nodeId,slot)` uniqueness; a concurrent plan revision or authority change still requires CP-09's recovery/transaction design. No API can ask this resolver to “trust” a fabricated authority row. Report any slot whose exact parent linkage is unavailable rather than widening the resolver.
