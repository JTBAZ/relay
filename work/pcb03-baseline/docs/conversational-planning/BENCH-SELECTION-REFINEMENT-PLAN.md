## Current behavior and bounded state

`src/editor-bench/chat.ts` already asks the model for `selection.mode` (`preserve|replace|add|remove`) and a `MetadataSelector` with `base`, `all`, `any`, `none`. `selector.ts` grounds each predicate's `requestQuote` in the **latest** request and deterministically resolves it against owned fixtures. The UI sends current post/media IDs but no refinement context. Thus a later `add` can reintroduce posts excluded by an earlier turn, and a model `replace` can silently discard an additive selection.

Add an optional top-level `refinementState` only to curation `free_text` requests. A legacy four-key request remains valid and keeps its existing execution semantics; a successful selection-only curation response may append the optional state, which old clients can ignore. The UI sends `null` on its first refinement turn and the exact state returned thereafter. The server rejects unknown keys, foreign/duplicate IDs, wrong fixture revision, overlong arrays and a mismatch between `selectedPostIds` and `refinementState.selectedPostIds` before calling the provider. Media IDs remain derived from selected posts, as today. The bounded wire is:

```ts
type BenchRefinementState = {
  v: 1;
  fixtureRevision: number;
  selectedPostIds: string[]; // BENCH_IDS.posts order, <=16
  excludedPostIds: string[]; // BENCH_IDS.posts order, <=16
};
// POST /api/editor-bench: existing body + refinementState: BenchRefinementState | null
// Successful selection-only response: existing BenchResponse + refinementState
```

This is a **fixture snapshot**, not a predicate-history language. Prior positive criteria are represented by the accepted selected IDs; prior exclusions by accepted excluded IDs. The only original-quote provenance needed for a new criterion is checked at the turn where it is accepted. The server resolves date predicates with that turn's trusted London clock, freezes resulting IDs and never re-grounds an old quote in a new request or lets `last_month` drift later. The state is client-carried but has no authority outside the fixed owned fixture; it is fully shape/revision/ID validated, and no arbitrary real post or media ID can enter. If the fixture changes, reject the stale state and ask for Start over. Supporting mutable catalogs or auditable predicate histories is a later design.

## Deterministic patch semantics

Keep the existing selector schema and one-call provider runtime. With state present, the model sees the latest request, current selected titles/IDs and excluded count, not a transcript or instructions to reconstruct past criteria. It emits **only this turn's** predicates. Every new `requestQuote` still must be an exact latest-request substring; existing description/date/unique-name rules and selector target guards stay. Selection-only means `intent:null` (or the existing accepted empty curation no-op). If a turn with non-null state includes an edit and `selection.mode='preserve'`, compile that edit against the already selected posts with no refinement-state change. If that non-null-state turn combines a selection change with an edit, clarify with no selection/cart/state change: refine first, then edit. Legacy requests and initial null-state edits keep their existing behavior, including a named rename from an empty selection. A successful initial edit can update selected IDs while keeping refinement state null; the first accepted selection-only turn seeds the bounded state.

For a valid selection-only turn, let `S` be prior selected IDs, `X` prior excluded IDs, `T` the new selector's deterministic matches, and `N` the union of matches for each new `selector.none` predicate resolved against the **full catalog** using the latest request/clock. New `none` exclusions apply globally for positive add/narrow/initial replace. For `remove`, `none` is an exception that limits the removal set; it is not a new global exclusion. Canonicalize every result to `BENCH_IDS.posts` order and deduplicate:

| Model mode | Allowed stateful selector | Next state before exclusion |
| --- | --- | --- |
| `preserve` | `selector:null` | `S` |
| `add` | `base:'catalog'` or `base:'selection'` | `S ∪ T` |
| `remove` | grounded selector | `S − T`; let `R` be the whole removal selector resolved against the full catalog, including its `none` exceptions, and add only `R` to `X` |
| `replace` | **only** `base:'selection'` | `S ∩ T` (a narrow) |

Then for add/narrow/initial replace, `X' = X ∪ N`; for remove, `X' = X ∪ R` and **not** `N`. Finally `S' = candidate − X'`. Thus “Remove sketches except coastal ones” keeps coastal sketches selected and eligible for later adds, while removed non-coastal sketches stay excluded. A stateful `replace` from `catalog`/`empty` is a clarification, never a silent reset. A selector with `none` but no positive scope cannot turn an exclusion-only follow-up into “add the whole catalog”; model should express “exclude sketches” as `remove` with a sketch predicate. A known literal description query with zero matches is valid: add leaves the prior selection unchanged, while narrow may commit an empty selection. A valid selection-only narrow or exclusion may produce an empty `S'`; commit that empty selection and state before the older `no_edit_targets` guard, which applies only to edits. Invalid, unsupported or ambiguous clauses, malformed output, provider failure and compiled-edit failure leave both selection and refinement state unchanged. The reducer returns `result.refinement` with operation, newly matched IDs and excluded IDs for readable diagnostics, not a new candidate UI.

For “Add the entire City studies series and everything whose description mentions neon,” the new selector uses `mode:'add'`, `base:'catalog'`, and **two `any` predicates** (`series_id`, `description`) with distinct latest-request quotes. Their union is added once; sticky exclusions are subtracted. If the model uses `all` and thereby narrows this explicit union, that is an interpretation error; the prompt must state the `any` contract and focused tests must catch it. General nested Boolean queries remain unsupported and must clarify.

Start over is an explicit, no-model reset: add a small `replay:{kind:'selection_reset'}` branch for curation. It clears selected and excluded IDs and returns an empty v1 state. After validating that response, the UI clears its active state to `null`, so the next request can make a fresh catalog selection. An ordinary empty narrowing result retains its non-null state and exclusions. The UI may route only exact “start over”/“reset selection” input to this branch; compound reset-plus-query requests clarify and require two turns. A normal model `replace` never clears exclusions. This keeps reset behavior reviewable and avoids a second broad language parser.
