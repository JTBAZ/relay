## Existing seam and the unsafe shortcut

`web/lib/relay-extension-messaging.ts` sends `RELAY_CROSS_POST`; `extension/src/background.ts` checks the Relay web origin and dispatches to `cross-post-flow.ts`. That flow fetches a bearer-authenticated package, stores it, opens a destination tab and injects the existing fill script. `extension/src/content/fill-x-compose.ts` consumes an X package and leaves the native Publish action to the user. Existing post-ID package routes in `src/server.ts` call `buildRelayCrossPostPackage`, which reads the **latest** post title/presentation/media. Its `buildCrossPostMediaEntries` silently omits missing IDs and puts images before non-images. The distribution-attempt branch applies a variant and updates attempt status. Neither branch can carry an event's literal title and exact saved media subset/order; do not send the source post ID through either branch or create an attempt merely for transport. The extension currently chooses its tab from the message destination before fetching, so the new path must cross-check it with the API response.

The confirmed real event already owns `postId`, ordered `mediaIds`, `title`, destination and status on `CreatorScheduleEvent` (see `BENCH-LIBRARY-ATTACHMENT-PLAN.md`). The current bench receipt in `web/app/editor-bench/EditorBenchClient.tsx` is the UI entry point. Do not add a Schedule Rail/EventPopover action in this slice; that persistent affordance is later work. The existing `schedule-reminder-extension-api.ts` CTA and `EventPopover` post-details path are different workflows and must not route this event into Autopost or a distribution review.

## Frozen transport and package

Add a development-only, side-effect-free `GET /api/v1/extension/cross-post/schedule-events/:event_id` in `src/server.ts`. Require a valid `SessionKind.extension` bearer grant, resolve its account's primary creator, and enforce the current Studio Core gate. Accept only a creator-owned `bench_event_` ID whose row is `pending`, `make_post`, destination `x`, `postId` present, `externalUrl:null`, `remindMe:false` and has one to three distinct real `mediaIds`. Read explicit event columns so unrelated unmigrated CP fields are not required. Re-read the owned active Library post's latest version and all selected `MediaAsset` rows; every saved ID must still be in that version, associated with the post, active, READY and either `image/jpeg` or `image/png`. Refuse a missing, changed, foreign, processing or non-JPEG/PNG item, an empty title, or an X title over 280 UTF-16 code units. Never filter, truncate, reorder or substitute a current Library title/media. The current-version membership check means a later Library edit that removes selected media blocks handoff; it does not rewrite the event.

Success uses the existing API envelope with `Cache-Control: private, no-store` and exact data:

```ts
{
  schedule_event_id: string,
  destination: 'x',
  package: {
    relay_post_id: string, // saved event.postId, for existing X package parser
    title: string,         // saved event.title
    body_text: '',
    post_text: string,     // exactly saved event.title
    media: Array<{media_id:string, filename:string, mime_type:string, content_url:string}>
    // exactly event.mediaIds order; one entry per ID
  }
}
```

Use `filenameForMedia` and `crossPostMediaContentUrlPath` from `src/extension/cross-post-media-entries.ts` for each validated media row, but not `buildCrossPostMediaEntries`. The export route remains the existing extension bearer media-byte authority. A syntactically valid export URL does not prove bytes can be fetched or attached; that awaits deferred browser fill proof. No export job or conversion is started here. The GET has no DB write and is repeatable for unchanged event/source facts; a repeated user click may open another compose tab but cannot create a second event or attempt. A successful launch means only that the compose tab opened and injection was attempted, not that filling or publication succeeded.

Extend `ExternalCrossPostMessage` in `extension/src/lib/cross-post-types.ts` as a strict disjoint branch `{type:'RELAY_CROSS_POST', schedule_event_id:string, destination:'x'}`. This branch rejects `relay_post_id`, `distribution_attempt_id`, `content_override` and absent/other destination rather than falling through to legacy post/attempt fetch. `cross-post-fetch.ts` fetches the fixed schedule-event route with the extension grant, requires response `schedule_event_id` to equal the request and response `destination==='x'`, parses the nested package with existing `parseXCrossPostPackage`, requires its `relay_post_id` to be nonempty, and stores it **without** `pending_cross_post_attempt_id`. Fetch/flow success also echoes the exact `schedule_event_id` and `destination:x`; the web helper checks both alongside tab/post IDs before acknowledging launch. `cross-post-flow.ts` uses the checked fetched destination to open X, avoiding a message/response tab mismatch. Fill-result and post-link reporting are attempt-ID gated already; no event completion is inferred. Legacy post-ID and attempt messages retain their behavior.

The web helper adds a separate `sendRelayScheduleEventToExtension(eventId)` that sends only the event-ID branch to a configured official extension. In the saved real-X receipt, render **Open X with extension** only when the confirmed row has the real attachment and X destination; use a per-click busy guard and surface grant/package/tab errors. Never call it automatically after Confirm. Copy says the selected images and event title will be placed in X Compose and the creator must review and press Publish there. No UI claim that the post was filled, posted, linked or marked done follows from the extension's `ok` response.
