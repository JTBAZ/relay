## Attachment authority and side effects

The current `POST /api/v1/creator/schedule-rail/events/:id/attach-media` is **not** the authority for this flow. It rejects an unlinked manual cue. Given a linked post, `attachMediaToScheduleRailEvent` rewrites that post's latest `PostVersion.mediaIds`, changes `MediaAsset.postIds`/`primaryPostId`/`autopostDraftId`, and may sync draft or Goal Cycle projections. Calling it would edit the original Library work. `createScheduledPostForRail` creates a new Relay Post, Autopost draft, distribution plan, variants and tasks; the conversational draft reservation path accepts unassigned staging assets rather than selected media already associated with a Library post. A live link to a post also cannot preserve an event-specific subset: `CreatorScheduleEvent` has `postId` but no media list, and manual rail rows currently report `media_count:0`, `media_ids:[]`.

Add **one** event-owned `mediaIds String[] @default([]) @map("media_ids")` field to `CreatorScheduleEvent`, with an isolated additive SQL/Prisma migration that does not depend on pending CP plan tables or `conversational_step_key`. This is an ordered snapshot of media **references**, not a snapshot of files. Persist it on the existing manual-event row alongside `postId`; do not use a JSON note, shadow table, cloned draft or mutation of the source `PostVersion`/`MediaAsset`. Update `CreatorScheduleEventWire` and the manual Schedule Rail projection to expose the selected `media_ids` and count for linked events; existing unlinked events naturally have `[]`. If a selected asset is later deleted or becomes unavailable, the rail must report a missing/unavailable media state rather than assert that a usable file is attached. A later Library post edit does not silently rewrite the event's selected IDs/order. The targeted migration is a required local proof gate before running the new code against the ordinary database; root owns the controlled apply and rollback/cleanup plan, not the workers. No full migration deploy is part of this ticket.

The real review presents the source title, selected media names/order, each destination/title/local time and an explicit notice: these are manual publishing cues referencing selected Library media, with no automatic posting.
