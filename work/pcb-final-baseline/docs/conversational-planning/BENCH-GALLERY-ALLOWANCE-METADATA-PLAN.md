# BLC-04: several-hundred-post mock selection without sending every family ID

Status: **BLC-04 accepted for the bounded mock metadata connector, 2026-10-18. Sol High planned, Luna High implemented, root reviewed and passed the quality/cost gate.** BLC-03 accepted one 112-entry mock vocabulary, but that profile reused one work across 1,001 posts. This ticket addresses ordinary galleries with hundreds of distinct works. It does not set prices, enforce a paid tier, or activate a live Library.

## Provisional allowances and evidence limit

Use **100 active posts included / 500 active posts expanded** as provisional product-design targets for gallery selection. They are round engineering targets, not billing entitlements or storage promises. Media bytes, upload/storage allowance, traffic, inference frequency, and margin need separate real usage data before price or billing implementation. The accepted BLR full-snapshot matcher already has a 1,024-post ceiling; this work does not change it or enforce 100/500. The mock chat's metadata budget is a separate limit: a 500-post gallery can still need clarification when its complete generic facets or a single request's named matches exceed the byte bounds.

The current complete vocabulary sends every `{id,title}` for works, series, and collections. A read-only synthetic measurement with UUID-length IDs and descriptive names produced **12,697 vocabulary bytes at 100 distinct works / 50 series**, and **47,097 bytes at 500 distinct works / 50 series**, before adding many tags. Both exceed the existing 8 KiB vocabulary bound. Raising a count limit, shortening JSON keys, or raising the prompt budget alone would make routine turns grow with the number of works. Sending only the first page or first K names would silently lose late matches. BLC-03's 112 short-tag proof does not establish this case.

## Small mock-only metadata adaptation

Keep complete deduplicated **tags, publication states, media types/roles/statuses** across every post. Replace the always-sent `works`, `series`, and `collections` arrays in the mock model input with `mentionedWorks`, `mentionedSeries`, and `mentionedCollections`: scan the **entire server-owned snapshot** for every owned family whose complete visible title or full opaque ID occurs literally, case-insensitively, in the latest request. Include all duplicate-title identities, regardless of page or match position; sort deterministically. Retain the existing exhaustive `mentionedPosts` rule. This is a request-grounded name lookup, not keyword intent parsing, semantic search, ranking, or top-K retrieval. Never send arbitrary unmentioned work/series/collection names or UUIDs. If the set of literal matches is too large, clarify the whole turn before the provider; never truncate it.

The model still emits the **existing** `work_id`, `series_id`, or `collection_id` predicate with an exact request quote; the offered pair supplies its opaque ID. The vocabulary guard must accept only a pair offered for this request and grounded by one unique full visible name or the literal full ID in that quote. Include pairs matched by **ID alone**, even when their title is absent from the request, and include every ID sharing a case-folded duplicate title. A duplicate full title with two IDs, an invented/unknown ID, a partial name, or an ID copied from a previous turn clarifies with unchanged state; prefix collisions keep the current conservative clarification behavior. The model must clarify a family request that lacks an offered exact name/ID (for example, a vague description such as “my most dramatic series”); it must not guess an identity or drop that criterion. **The current complete-vocabulary guard already refuses a family ID without its unique full name or literal ID in the quote.** Since `requestQuote` is itself an exact substring of `latestRequest`, exhaustive full-title/full-ID filtering cannot remove any family reference the current guard accepts. Vague family language remains outside the proven capability. The existing model-quality oracle, rather than a parallel natural-language parser, must detect an omitted criterion. Generic tag mapping, request-local date choices, literal description/title predicates, `all`/`any`/`none`, sticky exclusions, and shared full-snapshot matching/refinement remain intact.

Keep **one** configured cheap-model call, the 8 KiB complete generic-plus-mentioned vocabulary bound and 16 KiB serialized `{input,tools,responseSchema}` bound, request/date limits, state revision check, current response schema, and public BLR strict resolver. An overflow or ambiguity clarifies the full turn before committing state. Do not add a tool loop, embeddings, full index, full post-row prompt, model-generated ID enumeration, posthoc semantic repair, production route, or frontend integration. This is a narrower explicit language capability than showing every family name to the model; the tradeoff is disclosed rather than treating an incomplete catalog as complete.
