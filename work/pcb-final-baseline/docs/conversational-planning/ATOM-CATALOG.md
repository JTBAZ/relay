# CP-03 — Executable atom catalog (Accepted)

**Review state:** Accepted by parent architecture review, 2026-10-15, after CP-02 acceptance. This freezes the v1 action/authority mapping for CP-04a; implementation gates remain separate.

## Identity and authority first

A selected Library image is a creator-owned `MediaAsset.id`, not a post. Resolve `MediaAsset.creatorId` and `processingStatus`; then resolve a single creator-owned `Post` through `primaryPostId`/`postIds`, or a selected `CreativeWorkMember.postId`. A `CreativeWork` or `CreativeSeries` can contain several posts and does not itself anchor distribution. A missing or ambiguous post is a clarification. An upload-only staged image may enter an `AutopostDraft`, but no `PostDistributionPlan` exists until a real `Post.id` exists. A selected existing post can be the distribution source if the creator deliberately chooses it; do not mint a shadow post.

`AutopostDraft.workspace.source_post_id` already supplies read-only source context for nudged preview drafts. `AutopostDraft.publishedPostId` identifies a *Relay* post after `publishAutopostDraft`; it does not prove a Patreon publication. `saveAutopostDraft` only reserves READY, unattached staging media. Library art already attached to a post cannot simply be placed in a new draft's `mediaIds`; a safe reuse/copy or creator attachment path is an adapter gap for CP-09/11. A reference flow may prepare a title/copy draft with `mediaIds=[]`, but the UI must describe the missing media and prevent publish or preview export until repaired. For a creator-selected published source post, Previewizer may use that source art without claiming it is the new draft's art. An external Patreon publication still needs its own destination evidence.

## Finite v1 capability menu

The interpreter may propose only these IDs. The compiler chooses precise parameters and verifies creator ownership, entitlement, links and prerequisites. `prepare_post_draft`, `prepare_preview`, `prepare_distribution`, and `publish_handoff` are composition capability IDs, not new social-playbook keys. Publication is never an interpreter-executable capability. `publish_handoff` means a creator-visible task/approval path only. No arbitrary event type, platform, URL, tool call, or new social action can be supplied as a key.

|---|---|---|---|
| `prepare_post_draft` | Source `Post.id` or eligible staged `MediaAsset.id`, exact copy/title proposal, intended `patreon`; creates/reuses `AutopostDraft.id` and optional `CreatorScheduleEvent.id` attention. `AutopostDraft` owns draft content/status; event owns rail reminder. | Autopost gate for conversational flow. Prepared means draft row exists, not posted. `publishedPostId` is only a Relay post pointer. | Attached Library media is read-only in the draft service; no automatic reuse. Draft soft cap and existing active-draft behavior need CP-09 adapter design. Patreon external posting needs later variant/attempt. |
| `prepare_preview` | Creator-owned `CreatorPreviewTemplate.id` plus selected source `Post.id`/`MediaAsset.id`; creator opens Previewizer and explicitly exports. Template owns saved layout, exported `MediaAsset.id` owns preview media. | Autopost + Previewizer flags/ownership. Evidence is creator-owned ready `preview_media_id`, never publication. | Template config has no crop/selection; source-specific crop stays in Previewizer. Missing template/image blocks dependent teaser steps. |

The supported v1 destination set is exactly `patreon`, `x`, `deviantart`, `bluesky`, as declared by `CREATOR_SCHEDULE_DESTINATIONS` and distribution formatters. The reference plan uses Patreon for primary copy and X/DeviantArt for teasers. X/DeviantArt currently require the browser extension for form fill; Patreon readiness depends on creator ingest connection; Bluesky has an API credential path. A connection is a readiness check, never proof of a completed post. Plans with an unavailable destination remain reviewable with a repair slot; the affected handoff cannot start.

## Existing engagement atoms

`social-playbook-contract.ts` is the closed registry. These are **manual creator actions** scheduled/reminded or prepared as drafts; none sends comments or publishes externally. V1 conversational compilation offers only `reply_block` and `engagement_check` for the requested day+1/+2 example. All seven remain cataloged for later explicit opt-in; none is a synonym for vague “stoke engagement.” The legacy `applySocialPlaybook` requires a template and `anchor_due_at`, immediately computes `offset_minutes`, and materializes steps. It cannot directly implement publication-relative waiting; CP-13 needs a narrow new adapter without changing legacy due-at semantics.

| Registry key | Existing output / authority | Required target, evidence, and gap |
|---|---|---|
| `reply_block` | `CreatorSocialPlaybookStep` snapshot → `CreatorScheduleEvent(eventType=engage_comments)`; event pending/done/dismissed. | Explicit destination + published post target. Reminder completion is creator-marked event done, not proof of replies. V1 enabled after qualified publication evidence. |
| `engagement_check` | Same event type `engage_comments`; distinct title/note from template. | Explicit destination + published target. A reminder to inspect engagement; no metrics guarantee. V1 enabled after qualified evidence. |
| `pin_cta_comment` | Step → `CreatorScheduleEvent(eventType=pin_comment)`. | Explicit destination and existing external post/link; no API pin. Later capability, requires creator-selected CTA content. |
| `repost` | Step → `CreatorScheduleEvent(eventType=repost)`. | Explicit destination and published target; no API repost. Later capability. |
| `highlight_fan` | Step → `CreatorScheduleEvent(eventType=engage_comments)`. | Requires an actual creator-selected fan comment/UGC; never invent one. Later capability. |
| `cta_banner` | Step → `createScheduledPostForRail` → `PostbotTask`, `AutopostDraft`, Relay `Post`. | Needs asset/copy/format; prepared draft is not a published banner. Later capability. |

`CreatorScheduleEvent` is available to Studio Core for ordinary manual events, with `make_post`, `schedule_post`, `engage_comments`, `pin_comment`, `repost`, `custom` stored types. The conversational feature itself remains Autopost gated. Do not weaken Core manual event access or add an event taxonomy. `CreatorSocialPlaybookRun/Step` currently have unique `(creatorId,templateKey,anchorPostId)` and `(runId,stepIndex)` and snapshot existing template actions. That run family is template-bound, due-at anchored, and not a general conversational plan ledger. CP-13 may reuse its event materialization behavior, but must not force a synthetic template/run or mutate v1 offsets to represent the new plan.

## Publication evidence and timing authority

`PostDistributionAttempt` owns destination handoff status, `externalUrl`, `externalId`, `completedAt`; `PostDistributionVariant` owns destination copy/approval. `PlatformInstance` can hold a canonical platform URL. Current `completeDistributionAttempt` accepts `posted` even without a URL and the route defaults missing/invalid status to `posted`. The web UI has a distinct manual “confirm posted” action; the extension can also report a link after watching a filled composer. Therefore historic `posted` alone, a `PlatformInstance` alone, or a link inferred from a tab is insufficient for **new publication-relative anchors**. CP-12 must add typed evidence provenance on the authoritative attempt or its narrowly related publication evidence record, and require a creator-confirmed destination URL plus asserted publication time for X/DeviantArt/Patreon, or a successful API response with platform URI/CID and server time for Bluesky. Parse URLs with platform identity adapters, reject destination mismatch, and retain a clearly labeled creator assertion; do not market it as platform verification. Bare historical posted attempts require reconfirmation. See [PLAN-CONTRACT.md](PLAN-CONTRACT.md) for exact proposed schema and correction policy.

For each atom, `dueAt` and `status` belong to the authoritative event or draft/task. The plan contains only immutable requested steps, dependencies and pointers. A reminder packet is derived from `CreatorScheduleEvent` (`schedule_reminder:manual:{event_id}`), not stored in the plan. Plan approval is permission to prepare, not a posting receipt. The existing two Automations presets and their `CreatorDistributionRuleRun` ledger continue unchanged; they do not become a conversational chaining engine.

## Reference mapping

1. Resolve selected art to one creator-owned media/post identity; if multiple work members or no eligible post, show a source clarification. Verify “Part X” from a single `CreativeSeriesMember.partLabel` or explicit creator value; preserve explicit literal titles.
2. `prepare_post_draft` proposes Patreon title `Series Part X`. The creator reviews content/media and creates or links the real Relay post. Its `Post.id` becomes the canonical source for subsequent distribution; draft publishing alone does not prove Patreon publication.
3. Once the real Relay post exists, `prepare_distribution` may create the original-media Patreon variant and its separate `publish_handoff`. `prepare_preview` then uses one creator-owned saved template and waits for a source-specific Previewizer export. The adapter adds X and DeviantArt teaser variants with requested `Series Part X Teaser` titles to the **same active plan** through `reviseScheduledPostDistributionPlan`. It preserves an already handed-off/posted Patreon variant. Each teaser remains editable and has a separate `publish_handoff`.
4. Day+1/day+2 requests are unresolved until the creator selects a target destination/post and exact allowed action for each day. The reference target is X for both days. When qualified X publication evidence arrives, `reply_block` or `engagement_check` can become a due event. A failed or delayed DeviantArt handoff does not anchor or block X follow-ups.

## CP-03 negative findings to carry forward

- No current service converts an attached Library image into a new `AutopostDraft.mediaIds`; document and implement the selected-post/read-only or safe copy path before claiming a media-filled draft.
- `createPostDistributionPlan` is not idempotent for a conversation retry; it archives an active plan. Correlate and reuse the distribution group. `reviseScheduledPostDistributionPlan` can add later X/DeviantArt variants to that active plan and skips updates to posted/handed-off siblings. It sets a plan-level preview media ID and writes each new variant's `media_version=preview`, while the already posted Patreon variant retains `media_version=full`; CP-11 must prove this exact mixed-media journey and handle concurrent revision retries without a duplicate variant or archiving the plan.
- `startDistributionHandoff` creates a new attempt per call. Use a stable plan-step handoff key/locked pointer for request retries; a deliberate later retry after failure may create a new attempt.
- `CreatorSocialPlaybookStep.dueAt` is required immediately and `applySocialPlaybook` derives it from planned `anchor_due_at`, so a publication-relative waiting step cannot be stored there unchanged.
- A raw `posted` attempt, `PlatformInstance` URL, extension fill/link watch, or Relay `Post.publishState=published` cannot by itself satisfy an external destination publication anchor.
