# CP-07 — Composition persistence and correlation keys

**Review state:** Root approved schema authoring design on 2026-10-15 after integrated CP-06 acceptance (36 tests). CP-07a may author additive schema/DDL and run static/build checks only. Exact DDL review is still required before application to a fresh disposable test database; no migration of the ordinary database is authorized. This document proposes no schema or runtime change. [PLAN-CONTRACT.md](PLAN-CONTRACT.md) controls the wire shape and authority split; [COMPILER-PLAN.md](COMPILER-PLAN.md) controls the pure compiler gate.

## Storage boundary

Store one current `PlanSnapshot`, immutable accepted composition revisions, and pointers to existing authority rows. The plan has no execution status ledger: `AutopostDraft`, `CreatorScheduleEvent`, `PostDistributionPlan/Variant/Attempt`, canonical `Post`, and preview media remain the only execution authorities. A pointer records an identity, never a copied status, publication claim, due-state, failure, or result. Confirmation changes the plan's review state to `approved_for_preparation`; it does not prove preparation or posting. Keep `CreatorAutomation` and `CreatorSocialPlaybookRun/Step` unchanged.

Prisma/PostgreSQL naming follows `prisma/schema.prisma`: camel-case model fields, snake-case `@map`, plural table `@@map`, PostgreSQL `Json`/JSONB and `DateTime`/`TIMESTAMP(3)`. The exact proposed schema is:

| Model/table | Required fields | Keys and relations |
|---|---|---|
| `CreatorConversationalPlan` / `creator_conversational_plans` | `id String @id @default(cuid())`, `creatorId String`, `schemaVersion Int`, `revision Int @default(0)`, `review CreatorConversationalPlanReview`, `sourceRef Json`, `snapshot Json`, `clientCreateKey String`, `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt` | FK `creatorId` → `Tenant.relayCreatorId` (`tenants.relay_creator_id`, unique), `ON DELETE RESTRICT ON UPDATE CASCADE`; `@@unique([id,creatorId])` for creator-scoped child FKs; `@@unique([creatorId,clientCreateKey])`; `@@index([creatorId,updatedAt(sort: Desc)])`. `review` has exactly `proposed`, `approved_for_preparation`, `cancelled`; `schemaVersion = 1`, `revision >= 0`. |
| `CreatorConversationalPlanRevision` / `creator_conversational_plan_revisions` | `id String @id @default(cuid())`, `planId String`, `creatorId String`, `revision Int`, `clientMutationKey String`, `requestHash String`, `snapshot Json`, `createdAt DateTime @default(now())` | Composite FK `(planId,creatorId)` to plan `(id,creatorId)`; `@@unique([planId,revision])`, `@@unique([creatorId,clientMutationKey])`, `@@index([creatorId,planId,createdAt])`. No update endpoint for a revision row. |
| `CreatorConversationalPlanPointer` / `creator_conversational_plan_pointers` | `id String @id @default(cuid())`, `planId String`, `creatorId String`, `nodeId String`, `slot CreatorConversationalPlanPointerSlot`, `authorityKind CreatorConversationalPlanAuthorityKind`, `authorityId String`, `createdAt DateTime @default(now())` | Composite FK `(planId,creatorId)` to plan `(id,creatorId)`; `@@unique([planId,nodeId,slot])`, `@@index([creatorId,authorityKind,authorityId])`, `@@index([planId,nodeId])`. `nodeId` may name a step or group; a database check enforces the finite slot/kind matrix below. |

Use three dedicated Prisma PostgreSQL enums for the finite CP-04 `review`, `PointerSlot` and `AuthorityKind` values; use a migration `CHECK` for valid slot/kind pairs. Avoid an open-ended string vocabulary at the database boundary. The current-row `sourceRef` is an indexed/read convenience projection of `snapshot.source`, not a second authority: every write asserts deep equality. `schemaVersion`, `revision`, `review`, `id`, and `creatorId` likewise agree with the validated snapshot. The revision's immutable snapshot is configuration history, including user edits and review changes. It is not a record of whether anything ran. No raw transcript, image, provider payload, URL evidence copy, or mutable pointer list is embedded in snapshots. Enforce CP-04's 32-step, 16-slot and 64-KiB serialized UTF-8 bounds through `validatePlanShape` before writes and after reads; a JSONB text-length check is not a substitute for the exact wire-size rule.

`creatorId` is the Relay creator identity, **not** `CreatorProfile.id`, `User.id`, or `Tenant.id`. `Tenant.relayCreatorId` is the existing unique parent key (also used by `Account.primaryStudio`). Its nullable parent column is safe for this non-null child FK: a plan can reference only a tenant whose `relay_creator_id` is set. Existing headless `assertCreatorRelayMutationAllowed` verifies a Tenant only when `shouldVerifyTenantRow()` is true (configured by `RELAY_ENFORCE_CREATOR_TENANT` or `RELAY_CREATOR_ROUTE_SECRET`); other test/developer paths can have creator data without a Tenant. Do not describe that optional guard as a universal provisioning guarantee. CP-07's repository must check for the creator's Tenant and return a clear `creator_not_provisioned` failure before plan creation, while the FK remains the database backstop; it must not silently create a Tenant. A fresh database test must create a matching Tenant for positive cases and prove the absent-Tenant failure. Ordinary creator-owned authority rows do not all have parent FKs; this plan-specific FK does not retrofit them. `RESTRICT` prevents deleting a tenant while composition history remains; an explicitly reviewed account-erasure path deletes plan pointers/revisions/plan first, then proceeds with existing authority retention or deletion policy. Plan children may cascade only to their own plan for that explicit erasure path; no plan FK cascades into drafts, posts, events, variants, or attempts.

CP-08's new conversational-planning route must require a database-backed authenticated account whose `primaryRelayCreatorId` matches the requested creator **and** an existing `Tenant` with that `relayCreatorId`, on every create/read/revise/approve/cancel/pointer-facing operation. It must fail clearly for an unprovisioned creator and must not rely on the optional headless shared-secret guard or on `requireAccountMatchesCreator`'s test-mode `config.prisma` bypass as its sole protection. No implicit Tenant creation belongs in CP-07 or CP-08. Existing fixture/developer paths must provision a Tenant explicitly or receive the documented not-provisioned failure. This is a later route gate, not work for CP-07a's schema migration.

### Schema access and pointer constraints

Create the three tables in `public` with `ENABLE ROW LEVEL SECURITY` in the same migration, **no permissive policies**, and no `FORCE ROW LEVEL SECURITY`, matching the later creator-table lockdown migrations. Explicitly revoke table privileges from `PUBLIC` and, if those roles exist, `anon` and `authenticated`; do not add grants to browser/Data API roles. Do not add `USING (true)`, an unrestricted `FOR ALL` policy, or a `service_role` policy: such policies can expose full snapshots and pointers to a non-bypass role, and Supabase service roles already bypass RLS. The deployment design assumes the Relay API's configured Prisma database role bypasses RLS; that live role property has not been verified during this work and must still enforce authenticated `creatorId` filters and row checks. Review deployment grants before dispatch; if this API role is ever changed to a non-bypass role, require a separately reviewed scoped policy/session-context design rather than granting blanket access in CP-07a. Test catalog state (`relrowsecurity`, no permissive policies, no public/anon/authenticated grants); in the disposable database only, grant a temporary non-bypass fixture role enough `SELECT` to prove RLS still returns no rows, then remove that fixture. A privilege error alone would prove revoked grants but not RLS behavior. Do not assume RLS substitutes for application tenancy checks.

The database slot/kind `CHECK` permits exactly: `draft` → `autopost_draft`; `attention_event` and `engagement_event` → `schedule_event`; `relay_post` → `relay_post`; `preview_media` → `preview_media`; `distribution_plan` → `distribution_plan`; `variant` → `distribution_variant`; `current_attempt` → `distribution_attempt`. The enums and check reject an unknown vocabulary or mismatched pair even from a privileged writer. The database cannot check whether `nodeId` names a group or step within JSON, nor whether an authority belongs to a given source/group/destination. The pointer writer and reader enforce those graph and creator relations as specified below. No `ON DELETE CASCADE` pointer FK to any authority table is introduced.

Create revision `0` and the plan in one transaction. The initial revision uses `clientMutationKey=clientCreateKey` and a canonical create `requestHash`. Later accepted revise/approve/cancel mutations get consecutive revisions and distinct creator-scoped client keys. A plan and its revisions/pointers are retained on ordinary cancellation. Restrict routine plan deletion; only a separately reviewed account-erasure path may remove composition history, and it must not cascade-delete any independent draft, event, post, variant, or attempt. Child FKs must enforce creator equality with `(planId,creatorId)`; use `ON DELETE CASCADE` only from plan to its revision/pointer children for explicit erasure, and `ON UPDATE CASCADE` for key consistency. Polymorphic authority pointers cannot have one SQL FK to all authority tables, so the pointer writer and every pointer reader recheck expected kind, current creator ownership and parent relation under the authenticated creator.

### Authority correlations, nullable on legacy rows

Add `conversationalStepKey String? @unique @map("conversational_step_key")` to `AutopostDraft` and `CreatorScheduleEvent`, and `conversationalGroupKey String? @unique @map("conversational_group_key")` to `PostDistributionPlan`. PostgreSQL's nullable unique columns preserve multiple legacy `NULL` values and prevent duplicate non-null keys. The server constructs these keys, never the interpreter or client: `plan:{planId}:step:{stepId}` for the draft/event that a step owns and `plan:{planId}:group:{groupId}` for the one shared distribution plan. The same step key can appear in different authority tables only if the CP-04 slot matrix allows distinct outputs of that step; a second draft or second event for the same step is forbidden by that table's unique key. Do not retrofit legacy rows, and do not add publication or completion columns to the composition models. CP-12 may add a handoff-attempt retry key after its separate evidence review.

`distribution_plan` belongs to the group node once. `variant` belongs to its destination's `prepare_distribution` step; `current_attempt` belongs to its `publish_handoff` step; `draft`, `attention_event`, `relay_post`, `preview_media`, and `engagement_event` attach to the step that owns that output. A slot may have only its CP-04 matching `authorityKind`. A group may hold no step-only slot. The destination variant must belong to the group's `PostDistributionPlan`, match its destination, and be unique under existing `(planId,destination)`. A handoff attempt must belong to that variant. A schedule event pointer must name a creator-owned event with the matching correlation key; analogous checks apply to drafts and group plans. An existing canonical post or preview export may be pointed to after ownership/source validation, without claiming it was created by this plan. CP-07b returns `authority_gap` for `preview_media`, `attention_event`, and `engagement_event` insertion and reads until later work supplies an accepted authoritative source/template/export relation or exact event/action mapping; ownership or a correlation key alone is insufficient. Reject stale/missing nodes, cross-creator IDs, wrong parent/slot/kind, and attempts to reassign an immutable authority pointer. `current_attempt` replacement is deferred to a later explicit creator retry flow; old attempts remain on their variant.

### Replay, compare-and-swap, and crash boundary

Define `requestHash` as a SHA-256 hex digest of a versioned canonical serialization. For create, hash `{creatorId, operation:"create", normalized creator request/selection}` **before** server-generated plan, step, group, and slot IDs or timestamps exist. Root ratified the revise distinction: for `revise_ai`, hash `{creatorId, operation, planId, baseRevision, normalized creator command}` **before compilation**, including exact latest request, bounded selections, and any bounded client-supplied server-issued target-handle references; for `revise_manual`, hash the same identity fields plus the exact validated sparse field patch. For approve/cancel, hash the identity fields plus the exact review command. [CP-07b-IMPLEMENTATION.md](CP-07b-IMPLEMENTATION.md) defines the closed command/handle schema; never hash arbitrary request JSON. Include explicit clears and exact title text. Exclude newly generated IDs, server-held handle bindings, fresh source fingerprint, provider output, current authority state, and transport-only headers/timestamps; existing input plan IDs and echoed handle references remain included. Structured clarification-answer fields stay deferred unless separately reviewed as closed, bounded, and fully hash-included. The exact canonicalizer is server-owned and tested, so reordered JSON object keys replay identically while changed fields/hash do not. Never log the payload to explain a mismatch. On create, lookup `(creatorId,clientCreateKey)` before recompiling: same hash returns the recorded revision plus the *current* plan/pointers; different hash returns an idempotency conflict. A concurrent unique-key race is caught, then re-read and compared. On revise/approve/cancel, lookup `(creatorId,clientMutationKey)` first with the same rule, before recompilation or current handle resolution; if new, validate expected `baseRevision`, then in one transaction run a conditional plan `updateMany` on `(id,creatorId,revision=baseRevision)` and insert revision `baseRevision+1`. A zero-row update is a revision conflict. A rolled-back unique or serialization conflict is re-read/retried only within a bounded policy; it never silently merges two different writes. Snapshot validation, creator authorization and source fingerprint validation occur before the transaction and are rechecked where concurrent source change matters.

Pointer insertion/replacement is a separate server-owned operation in CP-09/11/12, with unique `(planId,nodeId,slot)` as the race arbiter. It must verify the actual authority row by creator and expected parent, use the nullable authority correlation key for recovery, and insert the pointer atomically with authority creation **only if the authoritative service accepts the same transaction**. Otherwise, after a crash, query the authority by unique correlation key and repair a missing pointer after validation. A key without the expected authority is a scoped failure, never a fabricated success. Plan approval cannot claim pointer existence, and pointer existence cannot claim an authority's current status. Replays re-read live authority state.

Current service seams prove why the unique columns alone do not make CP-09 safe: `saveAutopostDraft(prisma: PrismaClient,...)` performs prechecks then opens its own transaction around create/media reservation; `createCreatorScheduleEvent(prisma: PrismaClient,...)` owns its event validation/creation flow; `createPostDistributionPlan(prisma: PrismaClient,...)` can archive an existing plan *before* its own creation transaction. None currently accepts a caller transaction plus correlation key. CP-07 adds columns only; CP-09/11 must add narrow service overloads or an equivalent recoverable creator-scoped reserve/requery path and prove no duplicate or premature archive. For Patreon-first groups, later X/DeviantArt teaser variants are added to the same plan through `reviseScheduledPostDistributionPlan`, never a second `createPostDistributionPlan`. That revision service reads variant statuses outside its write transaction; CP-11 must re-read/lock or conditionally update a draft variant before editing, because concurrent handoff can make the initial status stale.

## Bounded implementation tickets

**CP-07a — schema and additive migration.** Owner: `prisma/schema.prisma`, one new sequential `prisma/migrations/<timestamp>_creator_conversational_plans/migration.sql`, and a focused static schema/migration test. Add the three composition models and three nullable authority correlation columns above; no other authority fields. Use the plan→`Tenant.relayCreatorId` FK, composite plan-child FKs with the deletion policy above, three finite enums, the pointer slot/kind `CHECK`, `schemaVersion = 1` and nonnegative revision checks, uniqueness/index definitions, and additive DDL without rewriting or backfilling existing rows. Enable fail-closed RLS and revoke public/Data API grants on all three new tables in the same migration; add no permissive or service-role policy. No API/service edits. `prisma validate` and `prisma generate` must pass, plus focused static migration assertions and backend build. Parent approves exact DDL and access posture before CP-07b.

**CP-07b — persistence repository and database proof.** Owner: new `src/conversational-planning/persistence.ts` and `tests/conversational-planning/persistence.test.ts` plus a local-only PostgreSQL integration test; no distribution/draft/event service edits. Accept a server-authenticated `creatorId`, validated CP-04 snapshot and client keys; implement create/read/list-current/revise/approve/cancel and checked pointer insert/read. No route and no materialization. The repo uses `PrismaClient` and `@prisma/adapter-pg`; this repository layer may use an interactive transaction for its own plan/revision writes and a conditional `updateMany` CAS. Test replay same/different hash, two concurrent mutations at one revision, revision-0 creation, uniqueness, manual edit snapshot preservation, scope isolation, pointer slot/parent/ownership checks, cancellation and read-after-restart. Real PostgreSQL proof checks the repository's explicit `creator_not_provisioned` response for an absent Tenant and the FK's direct-insert rejection, plus cross-creator child FK, invalid slot/kind pair, and ordinary tenant deletion while retained plan history exists; verify fail-closed RLS through a non-bypass role in the disposable DB. A fake pointer target or foreign creator fails before insert and on read. No status or success is stored on a pointer. CP-08 consumes this repository only after parent acceptance.

For migration and DB tests, the harness creates an explicitly named **fresh disposable local PostgreSQL database** such as `relay_cp07_test_<nonce>` and passes only its derived URL through `CONVERSATIONAL_PLAN_TEST_DATABASE_URL`. A pre-existing local DSN may privately provide host/port/user/password as a **connection bootstrap** after strict parsing and loopback validation; it may be the developer's ordinary local `DATABASE_URL`, but its named database is never the test target and never receives `migrate deploy`. Reject a non-loopback host, an inherited target name, a target without the exact `relay_cp07_test_` prefix plus unpredictable nonce, a target that already exists, or any URL equal to the ordinary `DATABASE_URL` target. Connect to a safe maintenance database only to create the exact new name. Record the nonce/name as harness-owned state without logging credentials or full URLs. Point the child `prisma migrate deploy` process's `DATABASE_URL` **only** at that isolated derived URL after the guard passes; `prisma.config.ts` otherwise reads ordinary `DATABASE_URL`. Apply repository migrations without reseeding defaults, run focused tests with random creator IDs, close pools, and drop only the exact harness-created database after re-verifying name/host/ownership. On failure, report the retained exact test database name for manual cleanup rather than trying a broad drop. Never use a linked Supabase project, remote host, or production credentials. A test skip without local PostgreSQL is a skipped DB proof, not migration success. CP-07 cannot be accepted on static checks alone if the local database proof is required by parent review. The existing `tests/gallery-editor-postgres.integration.test.ts` demonstrates a guarded opt-in local URL pattern; it does not authorize use of its database or production migration.

**Acceptance gate:** Parent reviews CP-06's final node/group identity rules, the CP-07a DDL/RLS scope, CP-07b real-PostgreSQL race and tenant proofs, and every remaining CP-09/11 service gap before calling CP-07 accepted.
