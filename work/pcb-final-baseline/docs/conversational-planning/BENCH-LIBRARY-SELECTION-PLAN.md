## Boundary and catalog

Add a development-only, authenticated real-Library curation mode beside the existing fixture curation and real-Library manual-posting picker. The API loads **all active posts for the authenticated creator**, or refuses the request. Read `Post` with `creatorId` and `upstreamStatus=active`, ordered by `(createdAt desc, id asc)`, with `take:41`; reject 41 rather than describing 40 as the whole Library. Resolve the at-most-40 IDs through `resolveLibraryPosts` for current effective title, description and tag deltas (including an intentionally empty `relayDescription`), then add owner-scoped current `PostVersion.publishedAt`, `Post.createdAt`, `Post.publishState`, work/series/collection membership, and the current active media associated with each latest version. Refuse a post with no latest version instead of inventing its metadata. Count current media with an 81st sentinel and refuse over 80; do not truncate relation arrays or selector-relevant fields. Include active posts with zero media. Load only metadata; no images, exports, publication, or writes.

Use `stripHtmlForSearch` on effective description for the model and literal `description` matching: remove tags, decode its supported entities, collapse whitespace, case-fold for matching. Do not use raw HTML markup as searchable words. `created_date` means the stored Library `Post.createdAt` calendar day in Europe/London. For imported posts it is an ingest/gallery-order timestamp (often derived from publication), **not** the artwork's creation date. `published_date` uses latest `PostVersion.publishedAt`; null drafts do not match date predicates. Never substitute sync/ingest time for a missing publication date. Date operators and relative periods use the existing selector rules and a trusted `currentBenchRequestClock`, not a second parser or browser time. Show these date meanings in the UI. If the user asks for an ambiguous artwork creation date, clarify rather than silently using `createdAt`.

The supported real fields are `post_id`, `work_id`, `series_id`, `collection_id`, `tag`, `publish_state`, `title`, `description`, `created_date`, `published_date`, `media_type`, `media_role`, `processing_status`. Work and series IDs come from owned relations, never title similarity. Collection membership comes from owned `CollectionPost` rows. Media facets use only active, currently associated media; a missing facet is unknown, not a fabricated value. Real mode explicitly rejects `stage`, `media_label`, `filename`, `orientation`, and any unsupported predicate before applying selection. Literal unknown description text yields zero matches; unknown IDs/tags/relations clarify as in the fixture selector. Every predicate retains the latest-request exact `requestQuote` grounding, including literal description text and supported date phrases.

Refuse the entire catalog before model dispatch when any title exceeds 200 characters, plain description exceeds 2,000 characters, tag/relation label exceeds 200 characters, or serialized model-facing catalog exceeds **48 KiB UTF-8**. Do not truncate text and create false negatives. API errors identify `catalog_too_large` or `catalog_incomplete` and ask the user to narrow Library externally; this slice has no partial-catalog query mode. Empty complete Library is valid. These bounds make the cheap one-call model context honest, not a billing guarantee.

## Exact wire and authority

API `GET /api/v1/editor-bench/library-selection/catalog` is development-only, uses `authenticateCreator(req,{readonlySession:true})` and creator scope, and requires no Studio Core publishing gate. It returns an API envelope whose `data` is:

```ts
type RealCatalog = {
  scope: 'real_library'; catalogRevision: string; complete: true;
  supportedFields: readonly string[]; timezone: 'Europe/London';
  posts: Array<{
    postId: string; title: string; descriptionText: string; tags: string[];
    createdAt: string; publishedAt: string | null; publishState: string;
    workId: string | null; workTitle: string | null;
    seriesId: string | null; seriesTitle: string | null;
    collections: Array<{ id: string; title: string }>;
    media: Array<{ id: string; mimeType: string | null; role: string | null; processingStatus: string }>;
  }>;
};
type RealRefinementState = {
  v: 1; scope: 'real_library'; catalogRevision: string;
  selectedPostIds: string[]; excludedPostIds: string[];
};
```

`catalogRevision` is SHA-256 over a stable encoding of authenticated account ID + creator ID + **all normalized selector-relevant post metadata**, including work, series, and collection names, in canonical post/media/relation order. It is a change detector and owner partition, not a secret authorization token. Rebuild the full snapshot on every turn. Reject a non-null state if its revision differs or if selected/excluded IDs are duplicate, unknown or out of canonical order. Do this **before** provider dispatch. A client may choose only among current owned IDs; it never supplies titles or a catalog to the model. If state is stale, return HTTP 409 `stale_library_selection` with no selection mutation; UI offers explicit reload/start-over. No HMAC, session table, migration, or write authority is needed for selection-only state.

Next `GET/POST /api/editor-bench/library-selection` is development-only. It forwards only the incoming cookie to the fixed API path using existing trusted `RELAY_API_BASE`; it does not accept caller URLs. `POST` enforces same-origin and `MAX_BENCH_BODY_BYTES` before API/provider work. Abort/cancel, invalid body, unauthenticated API read, stale state, and catalog overflow all stop before provider dispatch. Request:

```ts
type RealSelectionRequest =
  | { kind: 'select'; latestRequest: string; state: RealRefinementState | null }
  | { kind: 'reset'; catalogRevision: string };
```

The `select` path reloads/validates the authenticated API catalog and state before the existing `createEditorBenchRuntime` provider is invoked **once**, with the bounded server-owned catalog and latest request. The Structured Outputs root is an object `{result: anyOf(selection, clarification)}`; `result` is exactly `{kind:'selection', selection: MetadataSelection, intent:null}` or `{kind:'clarification', question:string}` (question max 1,000). A root-level `anyOf` is not used; no edit/posting intent is accepted. A clarification, malformed output, provider error, unsupported criterion, or stale state leaves IDs and exclusions unchanged. `reset` is model-free but also reloads the authenticated catalog and verifies revision; it returns empty selected/excluded state. After validating this response, the client sets its state to `null` so the next turn can be a fresh catalog replace; an ordinary empty narrow result keeps non-null state. For model-free checkbox changes, a narrow `kind:'toggle',catalogRevision,postId,selected,state` request may be handled against that same freshly loaded snapshot: check adds that ID and removes only its exclusion; uncheck removes and excludes only that ID. This preserves every other sticky exclusion without an extra model call. All successful responses are raw Next JSON, not the API envelope:

```ts
type RealSelectionResponse = {
  scope: 'real_library'; status: 'selected'|'unchanged'|'clarification';
  message: string; selection: { postIds: string[]; changed: boolean };
  refinementState: RealRefinementState; result?: { selector: MetadataSelector | null; matchedPostIds: string[] };
  usage?: { calls: number; known: boolean; inputTokens: number|null; outputTokens: number|null; costUsd: number|null };
};
```

The exact request union includes `toggle` as `{kind:'toggle',catalogRevision:string,postId:string,selected:boolean,state:RealRefinementState}`. Do not return fabricated media IDs in selection state. The browser `GET` can proxy the raw catalog for tiles. Set `Cache-Control: private, no-store` throughout. Keep fixture `/api/editor-bench`, fixture refinement DTO, real posting review, and schedule endpoints unchanged.

## Deterministic selection semantics

Reuse the selector schema and date resolver, with a narrow real-metadata facet adapter and the shared BSR refinement reducer over the supplied canonical catalog/order and supported-field set. This avoids refactoring the whole fixture editor. Leave the fixture adapter and existing compiler/target guards in place. Real mode never passes real IDs into fixture `BENCH_IDS`, `runCurationBench`, `validateIntentTargets`, or posting review. The server, not the model, resolves `all`/`any`/`none` against the full current owned catalog. Initial no-state replace may search catalog; with state, `replace` must use `base:'selection'` (narrow). **Real-only add requires `selector.base:'catalog'`** so it can discover new posts; constrain the provider schema by mode and reject an add with `base:'selection'` or `base:'empty'` unchanged at runtime. Requests scoped only to the existing selection should use preserve or narrow, not add. The fixture BSR contract stays unchanged. Add unions unique matches in canonical order. Remove resolves the **whole expression including `none` as an exception** over full catalog, then stores removed IDs as sticky exclusions. For add/narrow/initial replace, `none` matches become global sticky exclusions, applied after union. Empty valid results commit empty selection/state. Repeated additions and removals are idempotent. Explicit reset clears IDs and exclusions. Old predicate quotes are never re-grounded on later requests: this slice stores only resolved ID exclusions, so a changed catalog invalidates the revision instead of silently replaying history. This is snapshot-only refinement, not a saved search.
