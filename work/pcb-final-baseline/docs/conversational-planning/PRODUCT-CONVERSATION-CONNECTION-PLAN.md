## Boundaries that every ticket keeps

- A creator's current Library post and version, effective title/tags, associated ready media, and collections/works/series come from the existing owned Library reads. Fixture `stage`, filenames, and other synthetic labels cannot be inferred from real metadata. A sketch request with no supported real field asks for clarification. Metadata-only interpretation never claims to inspect image pixels.
- Selection and exclusions persist across turns until the creator changes them. A request that combines selection with editing or posting, or names no unique source, asks for clarification. Read-only browsing never edits source data. A proposed source edit needs its own review and **Apply**; a Previewizer export, destination draft, schedule, and handoff each need their own separate confirmation.
- A source artwork title/tag edit changes Relay's effective Library presentation under the existing editor authority. Destination teaser copy belongs to its own variant. An export is a new creator-owned preview asset. None of these silently rewrites the original post version or publishes to Patreon, X, or DeviantArt.
- At every confirm, reload the creator, source version/effective presentation, media association/readiness, chosen template/export, current variant, and expected revision as applicable. Reject foreign, stale, missing, or replaced reviews. An exact successful retry returns the original receipt without duplicating a write, upload, task, attempt, or tab. A failed or partial operation does not imply publication.
- Preserve current authentication, entitlements, destination limits, data caps, and existing shared route behavior. Use the bounded catalog/retrieval that already exists; a large Library or oversized model input fails clearly without hidden top-K omission or a cap increase. Keep the model away from execution authority.
- Keep the existing cheap runtime and one model interpretation per submitted turn. No hidden heavier-model fallback, repair call, paid evaluation, token-cap increase, or billing work is introduced by these tickets. Sol High refines plans, Luna High implements the data-boundary tickets below, and root reviews each scoped change before its dependent ticket starts.
- Confirmed draft history keeps its pinned source version, copy and export. A later Library edit does not rebase that draft or replace its JPEG. Recheck current ownership and retained-asset availability without substituting newer source content; reject changed facts in an unconfirmed review.
- The accepted `/editor-bench` implementation stays an isolated regression reference. Do not expose its routes or relax its development-only guards in production. The product connection uses authenticated Gallery editor, Library, Previewizer, distribution, Rail, and extension authorities. PCB-01 may begin as an opt-in development read with mock writes disabled; later reusable integration stays behind existing product flags and capabilities until the separate product acceptance gate.

Verification stays inside the existing backend suites and HTTP harness. Use the existing isolated PostgreSQL fixtures for durable transaction/read-back checks, without touching a creator's gallery. Each ticket covers its changed path, ownership/staleness, exact retry and the stated regression boundary; no new evaluation framework or broad fault matrix. Reuse the bounded journey once the backend connections are ready. No paid check is scheduled here. The three historical distribution-package fixture failures remain recorded separately and do not authorize unrelated cleanup.
