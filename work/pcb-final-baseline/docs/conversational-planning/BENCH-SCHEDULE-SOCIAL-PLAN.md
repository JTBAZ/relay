## Architecture decision

The production planning contract deliberately accepts `primary_draft` only for Patreon (`src/conversational-planning/intent.ts`), and the compiler rejects teaser-only requests with `contract_gap` (`src/conversational-planning/compiler.ts`). A teaser needs a saved template, real export and distribution preparation. Never compile a fictitious Patreon source and relabel its event X/DeviantArt. Do not relax those production validators, invent a hidden primary step, or present an unconnected destination as a connected handoff.

Add a **discriminated, bench-only direct manual-event interpretation** alongside the existing `INTERPRETED_REQUEST_SCHEMA` in the single `runEditorBenchChat` provider response. The new branch has its own exact schema and pure validator; it never enters `compileNewPlan`. The existing CP shaped posting interpretation, mock graph/examples, curation cart and selector retain their current paths. The free-text turn still makes at most **one** `gpt-5.6-luna` / `none` call under the existing development ledger, with no retry, fallback, or paid call in implementation/tests. This branch is for an explicit request for exactly one direct, dated, titled manual X **or** DeviantArt posting event. Requests for drafts, teasers, templates, preparation, publication, follow-ups, multiple destinations or multiple events remain on the existing mock planner/clarification path and cannot be silently reduced to one saved cue. Model semantic accuracy beyond the bounded checks is unmeasured; strict shape/quote/source checks provide a fail-closed boundary, not proof that every natural-language clause was understood.

## Frozen interpretation and review wire

The new `intent` alternative in the existing `{ selection, intent }` envelope has **exactly** these keys (no CP `base_revision`, request array, graph node or client-authored event fields):

```ts
type ManualPostingEventIntent = {
  kind: 'manual_posting_event';
  destination: 'x' | 'deviantart';
  source_ref: { mode: 'selection'; id: null } | { mode: 'post_id'; id: string };
  title_text: string;
  time_kind: 'absolute_local' | 'weekday';
  local_date: string | null;
  weekday: 'monday' | 'tuesday' | 'wednesday' | 'thursday' | 'friday' | 'saturday' | 'sunday' | null;
  weekday_qualifier: 'this' | 'next' | null;
  local_time: string;
  timezone: 'Europe/London';
  time_text: string;
};
```

Use the existing strict `METADATA_SELECTION_SCHEMA` and `resolveMetadataSelector` before either posting branch. Only a selector-authorized single fixture post with one to three distinct associated fixture media IDs is eligible, matching BS-01's visible source rule. `source_ref` must be that selected post or the exact `selection` reference. The direct intent's title must be a nonblank, trimmed, at most 200-character literal substring of the latest request; `time_text` must be a nonblank exact contiguous substring. Validate the absolute-date or weekday field combination and require explicit `local_time` and the confirmed bench zone; other zones ask for clarification. Change `resolveAbsoluteTime`'s input type to the time-field `Pick<RequestIntent, ...>` it already reads, then call that existing function with a fresh server request clock. This small type narrowing is the only calendar-resolver change. Preserve its unqualified-weekday upcoming occurrence and DST rules; require the resulting UTC instant to be future. No second date parser, regex keyword router or time fallback.

The pure direct mapper returns either one canonical manual-event proposal or a concrete refusal. Its proposal/review contains fixture source title/media labels for display, literal event title, destination, resolved London local time and UTC due time, and the existing manual-event payload. It explicitly says sample media is not attached. The backend review POST revalidates untrusted latest request, interpreted intent and selection with the **same pure mapper and a fresh clock**; it does not trust the chat response or call the model again.
