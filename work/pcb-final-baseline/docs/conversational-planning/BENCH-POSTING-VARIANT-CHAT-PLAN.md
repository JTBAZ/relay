After authentication, enumerate all of that creator's currently eligible linked draft/pending X or DeviantArt variants; take a cloned current-state snapshot. Supply only short server-owned handles, destination, current approved text, current revision and the short source title needed to identify a draft. Treat every text field as untrusted data; do not send original descriptions, full media metadata, source snapshots, revision arrays, credentials or unrelated creators' records to the model. Do not accept client-supplied variant IDs, source copy, revisions or candidate catalogs as authority. If no eligible draft exists, clarify without a model call. Offer the **complete** bounded candidate set, never a hidden top-K; if candidate bytes exceed 8 KiB or the whole input plus strict schema/tools exceeds 16 KiB, clarify before calling rather than omit a tail. Bound the request to 4,000 characters and the current BPD-02 replacement limit to 200 UTF-16 code units.

Use `createEditorBenchRuntime` and its existing ledger-backed `gpt-5.6-luna`/`none` provider in the **API process** (injected provider in tests), with one structured-response call, zero tools, no retries or fallback. A small separate strict schema is warranted because the existing selection/plan envelope cannot represent a draft revision edit. Its output is an `edit` or `clarification` decision, a candidate handle, an exact target-reference quote, an exact literal replacement text and its containing request quote, or a concrete clarification question. No model-supplied write facts or edit token are trusted. The model is instructed to clarify for vague rewrite requests such as “make it punchier,” missing replacement text, multiple edits, or a target that is absent or ambiguous. For this first slice, the replacement must be supplied inside paired straight or curly single/double quotes. Its containing request quote includes those outer delimiters; the new text must equal the interior exactly, with no unescaping or inferred unquoted boundaries. Unquoted replacements clarify. The replacement must be an exact contiguous substring of the latest user request, with no paraphrase, case change, normalization, suffix, generated caption or truncation. The target quote must also be an exact substring, with a target-reference occurrence outside the replacement occurrence; replacement text mentioning another draft must never supply target evidence. Empty, malformed or ungrounded output clarifies with no token.

Server-side target resolution remains exhaustive over the complete candidate snapshot. Accept a model-selected handle only if its quote identifies **exactly one** eligible draft by its full current text, full source title, or full exposed handle/ID; alternatively, a destination reference (“X” or “DeviantArt”) is sufficient only when exactly one eligible draft has that destination. A reference matching zero or multiple drafts clarifies; the selected handle must equal the uniquely grounded draft. Never infer “it” from a client-supplied ID, choose the first match, or silently prefer the newest draft. The model may propose the intended target, but lexical uniqueness and creator ownership are checked independently. Keep these checks to literal catalog grounding, not a second natural-language intent parser.

Once grounded, call the **same BPD-02 edit-review builder** used by `/variant-edit/review`, passing the server snapshot's variant ID and expected revision plus the literal replacement. This requires only a narrow extraction of that route's current read-only validation/signing logic; do not duplicate edit rules or bypass its no-op result. If another edit advances the draft during the model call, the existing expected-revision check returns a stale clarification and no token. A successful chat response returns the identical BPD-02 preview and signed edit token; only `/variant-edit/confirm` can append a revision. After confirmation, the next chat turn enumerates current text and revision from the adapter, not the creation receipt, so follow-up edits target the latest draft. Copy-only edit chat does not re-read/rebase the original fixture. Existing V1/V2/V3 creation and BPD-02 direct review/confirm behavior remain unchanged.
