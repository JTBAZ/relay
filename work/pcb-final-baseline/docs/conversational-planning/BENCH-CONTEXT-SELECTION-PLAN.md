## Frozen meanings and wire

Keep existing `{ field, value, requestQuote }` predicates and add `description` as a text field. It matches a **literal, case-insensitive substring** of the effective visible post description, using the same precedence as the editor state: `presentation.relayDescription ?? version.description`. An empty Relay override is meaningful and must not fall through to the source description. Require the literal query `value` to appear in `requestQuote` case-insensitively; the quote itself must still appear exactly in the latest request. An unfamiliar literal description query is valid and yields zero matches, rather than an “unknown metadata value” clarification. Match only text metadata; do not infer pictured content, synonyms, topics or sentiment. The existing adversarial Aurora source caption remains untrusted data when projected into the bounded model catalog.

Add a separate exact date-predicate alternative within the existing `all`/`any`/`none` arrays:

```ts
type DatePredicate = {
  field: 'created_date' | 'published_date';
  value: string;
  requestQuote: string;
  op: 'on' | 'before' | 'after' | 'on_or_before' | 'on_or_after' | 'in_month';
};
```

The legacy three-key predicate remains valid unchanged; only date fields require `op`. `created_date` means the synthetic **Library post creation** date; `published_date` means that post's publication date. Neither means file upload or version sync. Add explicit varied `createdAt` UTC instants and `publishedAt` UTC instants/null to the 16 server-owned post fixture definitions. A draft has `publishedAt: null`; never substitute `syncedAt` or another date. Project bounded `description`, `createdDateLocal`, and `publishedDateLocal` into `createBenchOwnedCatalog` with the explicit `Europe/London` zone. The selector derives from those same fixture facts so the model-visible metadata and server match cannot disagree. No real DB field, migration, production reader or page UI change.

`on`, `before`, `after`, `on_or_before`, `on_or_after` take a valid canonical `YYYY-MM-DD` value. `on` also accepts `today` or `yesterday`. `in_month` takes valid `YYYY-MM`, `this_month`, or `last_month`. Compare **London calendar dates**, not timestamps: `before`/`after` exclude the named day; `on_or_before`/`on_or_after` include it; `in_month` includes the first through last day of that calendar month. `last_month` is the preceding London calendar month, not a rolling 30 days. The server resolves relative values from the already computed `currentBenchRequestClock(options.now)` passed as a **required trusted argument** into `resolveMetadataSelector`; there is no hidden `Date.now()`, host timezone or second model call. Validate real calendar dates/months, exact predicate keys, existing count limits, and each `requestQuote` as a nonblank exact substring of the latest request. For an absolute day, require its canonical ISO `YYYY-MM-DD` to occur in the quote. For an absolute month, require canonical `YYYY-MM` or its corresponding English month name plus year (a finite 12-name lookup) in the quote. For relative values, require the corresponding literal phrase in the quote (`today`, `yesterday`, `this month`, `last month`). Other date phrasings clarify; do not ask the model to normalize unsupported date text and then trust it. A syntactically valid date with no fixture match yields an empty selection under existing behavior; invalid/missing dates clarify, never broaden.

Keep every qualifier as its own predicate. For example, “select published posts created last month whose description mentions moonlight, except sketches” requires `publish_state=published`, a `created_date/in_month/last_month` predicate and `description=moonlight` in `all`, with the sketch criterion in `none`. The existing `validateIntentTargets` must continue to block edits outside that exact result; a zero-match edit leaves selection and cart unchanged. Prompt the cheap model using the bounded catalog and the explicit request clock; instruct it to represent **every** requested date/description/exclusion criterion or ask for clarification, never drop an unsupported one. Retain one configured `gpt-5.6-luna` / `none` call, the existing selector envelope, and no fallback/repair. The model must ask which date is meant for “posts from September” or “post date” when creation versus publication is unspecified. “Uploaded”, file dates, recurring periods, fuzzy description search, nested Boolean expressions and unsupported relative periods such as “last 30 days” clarify rather than silently map to another field. A draft's null publication date never matches a positive `published_date` predicate.
