## Route and controller contract

Base: `/api/v1/conversational-planning`. Root approved these exact opt-in settings: `RELAY_CONVERSATIONAL_PLANNING_ENABLED=1`, `RELAY_CONVERSATIONAL_PLANNING_ALLOWLIST` containing comma-separated exact creator IDs, and `RELAY_CONVERSATIONAL_PLANNING_AI_ENABLED=1` for new interpreter calls. Trim allowlist entries, discard empty entries, and compare exact IDs; an empty allowlist disables access and no wildcard is supported. Missing enable settings mean disabled. Do not change `.env` files or enable a running environment as part of CP-08. `capabilities` may explain disabled/AI/preparation availability to an authenticated owner; it cannot provision anything. Return existing success/error envelopes with a trace ID and `Cache-Control: private, no-store`.

| Method and path | Behavior |
|---|---|
| `GET /capabilities` | Authenticated, provisioned owner; read only. Report configured feature/AI/preparation availability and entitlement. No provider construction that can reserve budget or contact a network. |
| `POST /plans` | Interpret a bounded create command, compile, validate fresh context, and persist proposed revision 0 only for a `plan` result. Return source/target ambiguity as clarification with no write. |
| `GET /plans` | Creator-scoped `listCurrent`; strict bounded cursor and limit. No history export. |
| `GET /plans/:planId` | Validated current snapshot, live checked pointers, and bounded edit-handle descriptors. Foreign/missing IDs use the same not-found response. |
| `GET /plans/:planId/preview` | Deterministic review/readiness projection from the validated stored snapshot and checked authorities. No model call, snapshot creation, approval, pointer repair, or preparation. |
| `POST /plans/:planId/revise` | Closed AI/manual discriminated body, stable mutation key, and required base revision. AI calls the accepted revision compiler; manual edits apply only the accepted sparse patch. Persist one validated revision through repository CAS. |
| `POST /plans/:planId/approve` | Repository review command only. Advance review to `approved_for_preparation`; response makes no preparation/publication claim. |
| `POST /plans/:planId/cancel` | Repository cancel command/CAS. Retain composition history and authorities. No delete endpoint. |
| `POST /plans/:planId/confirm` | Typed preparation seam below. With no accepted production materializer, return `preparation_unavailable` before an approval write. CP-08 tests this seam with mocks; CP-09 makes it operational after review. |

GETs perform no persistent mutation: no compilation/model call, entitlement refresh write, pointer repair, audit-record creation, lazy provisioning, status update, or budget reservation. Session authentication may set its existing database session context; it does not authorize composition writes. Do not reuse a GET helper that creates defaults as a side effect.

The wire bodies have exact keys; route `planId` supplies the internal command's `planId`. Bodies cannot supply creator/account IDs, snapshots, context rows, source fingerprints, provider/model/pricing/budget configuration, current values, handle binding maps, status, or authority pointers.

```ts
type CreateBody = {
  clientMutationKey: string; latestRequest: string;
  selectedPostIds: readonly string[]; selectedMediaIds: readonly string[];
  selectedTemplateIds?: readonly string[];
};
type ReviseBody =
  | (CreateBody & { mode: "ai"; baseRevision: number;
      targetHandleRefs?: readonly { handle: string }[] })
  | { mode: "manual"; clientMutationKey: string; baseRevision: number;
      patch: readonly ManualFieldPatch[] };
type ReviewBody = { clientMutationKey: string; baseRevision: number };
type PlanningPrincipal = { accountId: string; creatorId: string };

interface ConversationalPlanningService {
  create(p: PlanningPrincipal, body: CreateBody, signal: AbortSignal): Promise<TurnResult>;
  revise(p: PlanningPrincipal, planId: string, body: ReviseBody, signal: AbortSignal): Promise<TurnResult>;
  get(p: PlanningPrincipal, planId: string): Promise<PlanReadResult>;
  list(p: PlanningPrincipal, page: { limit: number; cursor?: PageCursor }): Promise<PlanListResult>;
  preview(p: PlanningPrincipal, planId: string): Promise<PlanPreviewResult>;
  approve(p: PlanningPrincipal, planId: string, body: ReviewBody): Promise<PlanWriteResult>;
  cancel(p: PlanningPrincipal, planId: string, body: ReviewBody): Promise<PlanWriteResult>;
  confirm(p: PlanningPrincipal, planId: string, body: ReviewBody): Promise<ConfirmResult>;
}
```

Implement the named service result types as closed unions of existing compiler/interpreter/repository outcomes plus bounded API errors, not `unknown`, arbitrary provider JSON, or a generic success string. `TurnResult` distinguishes stored/replayed plan, clarification, limitation, unchanged, and unavailable/error. A `clarification_preview` is unpersisted. A valid partial plan may retain independent executable requests and explicit blocking slots only as allowed by CP-04; ambiguous source/target or a compiler clarification never creates a pretend valid snapshot.

## Authentication and entitlement

Every operation, including reads, preview, capabilities, replay and confirm, requires configured PostgreSQL identity and a validated existing cookie/Bearer session through `requireAccount(req, {prisma, identityService})`. Read the actual account-backed `primaryRelayCreatorId`, require it to match the requested scope, then explicitly query `Tenant.relayCreatorId`. Missing Tenant returns `creator_not_provisioned`; never create one. Construct `PlanningPrincipal` inside this server boundary. Service methods are internal, not a public way for request JSON to assert a principal. Every plan/source/authority query still carries the authenticated creator.

`requireAccountMatchesCreator` in `server.ts` currently succeeds when `config.prisma` is absent, and `assertCreatorRelayMutationAllowed` has optional tenant/headless behavior. Neither is sufficient authentication for these routes. Reject no-database, file-backed, unlinked-account, revoked/expired-session and secret-only access; developer mode changes none of these rules. Mutations also use existing Studio write-lock/sync restrictions after authentication. Preserve the existing session/CSRF/origin protections; do not introduce a replacement token scheme or a new headless exception.

Require effective Autopost or higher for this composition surface, consistent with the existing contract validator and automation minimum. Core manual schedule events continue through their existing endpoints. Map failure to `plan_required` with `required_plan:"autopost"`; do not accept a client feature flag or the legacy posting-assistant flag as Autopost entitlement.

**GET purity trap:** `requireCreatorPlanAtLeast` can call `resolveCreatorPlan`, which upserts/deletes `CreatorPlanEntitlement`. The production context loader and GETs therefore need a private **read-only** effective-entitlement resolver in `context.ts`: apply the same unexpired operator/pilot snapshot, accepted snapshot minimum, account-scoped active/trialing subscription and plan-rank rules with reads only. Do not call the mutating resolver from validation. Test parity with the relevant existing billing cases and assert zero upsert/delete calls. This slice does not refactor shared billing code or call Stripe. Missing or indeterminate entitlement fails closed rather than creating/upgrading a grant.

Independently re-read context before persistence, and preserve CP-07's remaining source-change/commit boundary: CP-09 must check drift again before preparation.

Query exact existing models, with explicit selected columns and creator predicates:

A name lookup is exact and capped; duplicate matches clarify, never pick the newest silently. Create and AI-revision context input accepts optional `selectedTemplateIds`: at most three distinct nonempty trimmed IDs, each at most 160 characters. For a nonempty explicit selection, load exactly those creator-owned rows and require the exact requested count; a missing/foreign ID fails closed. Reconstruct the accepted selection order rather than accepting database result order as command identity. Omitted/empty selection means no explicit selection: auto-offer the catalog only if it contains at most three templates. - Existing connected-platform service returns server readiness. Copy only destination/readiness into context. Its X/DeviantArt result is currently `needs_extension`; preserve that result. Do not turn it into `available` from client assertions or from the mere existence of a destination. A disabled handoff/repair slot remains necessary until an accepted server readiness seam proves otherwise. No credential/token/detail string enters the prompt.
- Root approved a direct creator-owned `CreatorPostingGoal.timezone` read as the creator-zone authority. Validate IANA form and freeze it once per request; missing/invalid setting yields null/`unknown_time`. Do not call a goal getter that creates defaults/upserts, use process/browser timezone, borrow a different creator's setting, or silently choose UTC. The existing stored setting is the authority; this does not establish new timezone-confirmation provenance. A changed setting does not reinterpret a stored absolute time.

Define a deterministic versioned source fingerprint over the actual selected source/media versions and creator-owned post/work/series relations relevant to compilation, with sorted identity sets. Keep full source values server-side. No request clock, new ID, provider result or mutable execution status enters the fingerprint. The repository loader must recompute it from actual rows, never echo `snapshot.source.source_revision`; template freshness/readiness/entitlement are checked separately by `TrustedPlanContext`. Cap relation expansion; exceeding the bounded candidate set returns narrowing/ambiguity, never truncation that changes source identity. `loadSourceRelations` and the repository loader must agree on the same real relations. The private compiler helper remains unchanged; shared production adaptation belongs here.

For AI revision, the model's template context may combine explicit `selectedTemplateIds` with the retained preview-template references relevant to the bounded edit scope; deduplicate by ID and require the combined context to stay within three. Otherwise ask the creator to narrow template/edit scope, without changing retained plan nodes or saved templates. This prompt limit does not cap server validation: the repository context loader must always freshly validate every retained preview template/config referenced by the snapshot, including relevant references omitted from this turn's prompt. A selected template is an offered owned reference, not authorization to replace another step's template or overwrite its manual edits.

Edit aliases are presentation references, not authentication tokens. Root approved `node_` followed by the first 24 lowercase hexadecimal characters of SHA-256 over a versioned canonical serialization of `[creatorId,planId,revision,stepId]`. Use the version-1 canonical envelope `{v:1,binding:[creatorId,planId,revision,stepId]}`, sorted object keys, preserved array order and UTF-8 encoding. Derive the map only from the server-validated current snapshot; detect any alias collision and fail closed rather than overwriting a binding. Return descriptors to its owner and reconstruct the identical map on a new request/restart. No raw-ID equality is an alias check, and no new DDL, signing key or token authorization scheme is introduced. Never derive authority from a client-supplied `stepId`/binding map. Require `baseRevision` to match before any new interpretation, and resolve supplied aliases only within that exact map. Manual patch step IDs are validated against the owned current snapshot.

At most 32 descriptors may be returned for a 32-step plan; each alias is 1–100 characters. AI requests expose at most eight targeted/current editable nodes to CP-05. Route `targetHandleRefs` therefore allows at most eight distinct exact `{handle}` objects, narrower than CP-07's 32-reference ceiling. If the plan has more than eight editable nodes and the creator supplies no bounded target scope, ask them to narrow; never choose by title similarity or silently omit a possible target. Every interpreter target handle must be in the supplied server context. Hash the actual accepted echoed refs through CP-07; omitted/empty normalize there to the same empty array. Replay lookup occurs before current handle resolution so an already recorded command can replay after its old aliases cease to be current.

## Limits, replay and mutation ordering

Enforce an exact-key wire schema before service work, with no arbitrary clarification-answer object. CP-05 limits govern AI requests: nonempty latest request at most `MAX_REQUEST_CHARS=4000` as enforced by `intent.ts`; at most three selected media and four selected/candidate posts; IDs also meet CP-04/07's stricter nonempty, trimmed 160-character bound; at most three template summaries, four destination summaries and eight editable nodes. Context JSON is at most 12 KiB, complete provider input at most 16 KiB, maximum six intents and 3,000 output tokens. Use `projectPlanningContext` and `interpretRequest` as the final text-only boundary and size check. Do not call on oversized data and hope the interpreter truncates it. Keep request/title/quote text exact; use a narrowing response when safe projection cannot represent it.

The optional `selectedTemplateIds` field exists only on create/AI-revise wire bodies and the corresponding persistence commands; manual revise, approve and cancel shapes stay exact and unchanged. Accept at most three distinct trimmed 1–160-character IDs and include the exact accepted nonempty array, preserving order, in the precompiler command hash. Omitted and empty arrays have identical no-selection behavior. **Preserve stored v1 replay hashes:** canonical hashing omits `selectedTemplateIds` entirely when absent or empty; do not add a new `[]` property to all historical command identities. Nonempty selections are included and a changed/nonempty selection conflicts under a reused mutation key. Existing `targetHandleRefs` normalization remains unchanged. Old clients may omit the field, and their existing no-template-selection hashes continue to replay without rewriting immutable revisions.

For HTTP bodies, root approved a 16-KiB JSON parser cap on this prefix plus the repository's canonical-command 16-KiB cap. `server.ts` currently installs global `express.json()` first; a second parser after it does not enforce transport size. The serial registration slice must install the prefix's bounded parser before the global parser, with no parser behavior change on other prefixes. Also enforce size on already-parsed test inputs. Test both Content-Length and chunked oversized requests; a header check alone is insufficient. No multipart/image payload is accepted.

Keys and plan/step IDs are bounded to 160 characters. Revisions are nonnegative safe integers. Manual edits reuse the exact `ManualFieldPatch` discriminators: title, note, enabled and time only; 1–128 entries, unique `(step_id,field)`, exact keys, note at most 2,000 characters, copy strings at most 500, and closed `CopyValue`/`TimeSpec` shapes with validated date/time/zone consistency. No model/client patch to creator/source/IDs/dependencies/review or authority fields. Apply patches to a clone of the current snapshot, preserve untouched siblings/groups and creation time, set server update time and revision once, and validate the entire result under 32-step/16-slot/64-KiB bounds. The repository independently verifies manual candidate equivalence. Explicit null clears are hashed as such; sparse omission means unchanged. Reject enabling a node with invalid/disabled prerequisites, not a silent graph repair.

For a stored mutation:

1. Authenticate account, explicitly check Tenant, feature/write restrictions and effective entitlement; validate the bounded body and construct the existing `Mutation` with server creator ID and exact operation.
2. Call repository `lookupReplay` before AI availability/provider/context construction, current alias resolution or compilation. A replay returns recorded revision plus freshly validated current plan/pointers; a collision returns 409. No paid call occurs on either path. This permits accepted commands to replay while new AI calls are disabled, while preserving ownership/feature/entitlement gates.
3. For a new revise/review, read and validate current plan; check base revision before provider work. Reject stale/terminal state. Load fresh owned source and bounded context, handle map and server clock. Create does not accept a client plan ID.
4. For create/AI revise, call `interpretRequest` once. Its single malformed-schema repair may make one additional provider call; service/controller add no retry. Missing information, visual request, no-change, terminal provider failure or compiler clarification causes no composition write. A clarification is answered through a new exact latest request and mutation key; structured answers remain deferred until separately reviewed as bounded and hash-included. Clarification/no-change outcomes have no stored revision, so the API must not claim durable replay of those outcomes.
5. Pass accepted intent into `compileNewPlan` or `compilePlanRevision`, real calendar resolver and fresh production `TrustedLookup`. Handle discriminated outcomes. Do not write a patch returned by the model or rerun a losing request against a later revision.
6. Recompute fingerprint/context and validate immediately before repository create/revise/approve/cancel. Use existing transactional CAS and immutable revision insert; a concurrent winner yields replay or conflict according to CP-07. No authority row/pointer is created here. Return checked current data, not stale compiler assumptions.

Lookup-before-provider eliminates paid work on recorded sequential replay. It does not claim global exactly-once model calls: two simultaneous new deliveries can both pass lookup before either commits. CP-07 still prevents duplicate accepted revisions. A durable cross-worker interpretation reservation would need separate root-reviewed persistence; do not invent one or use a process cache as proof. Bound each delivery to the existing two-call ceiling and ledger, test the race, and record this cost limitation.

## Confirmed time: root's bounded v1 decision

Root selected v1 behavior on 2026-10-16: supply **no `confirmedTimes` evidence** unless actual persisted trusted provenance exists. None currently exists. Keep the pure compiler hook unchanged and pass no invented evidence. `PlanSnapshot.time`, immutable revision snapshots, a creator-origin title, plan approval, request hashes and the survival of a value across revisions do not prove that local time was explicitly confirmed. A request hash cannot reconstruct a manual patch or its meaning.

Therefore “move the X teaser to next Friday” without local time returns the existing `unknown_time` clarification, even if the proposed plan currently shows 17:30. “Move the X teaser to next Friday at 17:30” can resolve under the validated frozen creator zone. Manual time edits persist their typed values but do not automatically establish reusable confirmation provenance across restarts. Model `editable_nodes.time_origin` must remain null for stored times with unknown provenance; never mark every stored time as creator-confirmed. Display the saved proposal as a proposal and ask for the needed local time.

This is an explicit bounded UX limitation of API v1. Any later inherited-time feature needs a separate reviewed ticket for bounded composition provenance, its exact creator/plan/revision/step/value binding and validation. It is not an execution ledger. No CP-08 DDL, new confirmation token or session-only assertion is authorized by this plan.

Do not echo arbitrary exceptions or raw repository/provider data. Existing response-envelope conventions control final casing.
