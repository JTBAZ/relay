## The seam

Next currently owns the curation selection displayed by the page, while the API process owns the ephemeral BPD posting variants. The curation compiler and selector also rebuild revision-7 fixture data on every call. That loses a confirmed rename or tag change on the next turn. BCT-01 adds one API-instance, creator-bound mock conversation store beside the existing BPD adapter. Each opaque session holds a clone of the fixture's effective state, ordered selected and excluded post IDs, a monotonically increasing revision and turn generation, one pending review, and the small edit-receipt/confirmed-token pointers needed for retries. The existing BPD adapter remains the owner of created variant and event records. The source fixture and its staged manual action are never changed. An authenticated creator can start a session, use it from one browser tab, and discard it; a missing or expired in-memory session asks them to start again. The session ID is an opaque lookup key, not authority to submit posts, copy or revision facts. Put a modest per-creator/global count and idle expiry on this temporary store so abandoned tabs cannot grow it without bound.

Add one **Conversation** choice to the existing bench composer. It keeps the same textarea and chat display; old modes remain available. In Conversation, the page starts a session and sends only the session ID, expected revision and latest text to the API. The server returns current cards, selection, revision and either a selection result, edit preview, posting review or clarification. The grid must use those returned cards after a confirmed edit; it must not redraw from the old static Next catalog. Starting another turn invalidates an unconfirmed preview in the page and on the server. A slow model response is discarded if its turn generation or revision is no longer current. No client-supplied fixture, selected IDs, interpreted intent or chat transcript is trusted as state.

Interpret one text turn with one call to the existing ledger-backed cheap model in the **API process**, using a small strict union: selection-only, one post rename, one post-level tag delta, one direct manual X/DeviantArt cue, or clarification. Reuse the metadata selector schema and exhaustive `resolveMetadataSelector`/`applySelectionRefinement`. The edit and posting branches contain only their required literal fields and quotes; do not include the full universal curation intent schema or run a second classifier call. A bounded complete current catalog is supplied as untrusted data. Preflight the exact serialized input/tools/schema at 24 KiB and clarify on overflow before provider use; never hide candidate posts with top-K truncation. The old chat/schema/provider paths keep their defaults. A turn may perform **one** of these operations. If the user combines a selection change with an edit or posting request, asks for multiple edits, or names no unique source, ask them to split or clarify. Pure selection updates selected/excluded IDs and revision immediately. It does not change post metadata.

Thread an optional trusted fixture through the existing catalog, selector, curation compiler/simulator and direct manual-posting helpers; omitted arguments still construct the original fixture for legacy callers. `createBenchPostCards(fixture)` must derive effective tags from its version and post override, as it already derives the effective title. This is needed for a confirmed tag change to appear in the next catalog, selector match and posting source. Keep the original title, version/media rows and unrelated staged action intact. For an edit turn, require exactly one selected, uniquely grounded post and either a literal rename or one post-level tag-delta operation. Build the existing strict structured intent from that narrow model output and check its new title/tag values against exact request spans. The curation compiler's output includes the fixture's pre-existing staged manual action. Require that baseline action list to be unchanged, extract only the newly compiled `rename_post` or post-level `tags` action, and simulate **only that delta** on the session's effective state for the read-only before/after preview. Reject other newly introduced actions. Confirm likewise applies only the new delta: it neither commits nor drops the baseline staged description action. No edit is applied on preview.

Edit Confirm uses a compact signed review token bound to creator, session, active pending ID, revision, action digest and expiry. The API rechecks the active pending review and revision, applies the already compiled action to the cloned state atomically, increments revision, and returns refreshed cards and an immutable receipt. Replacing a pending review or advancing the session makes its old token stale. An exact successful token retry returns its saved receipt without applying the action again, even after later turns. A different stale token conflicts. Selection remains stable across confirmation unless the user explicitly changes it.

For posting, require exactly one current selected post and one to three associated ready sample images, within the destination's media limit. Ground a literal X or DeviantArt title and future Europe/London time through the existing manual-event mapper and `reviewBenchSchedule` with the session fixture. Give this path its own compact signed **conversation pending envelope** bound to creator, session, active pending ID, revision, payload and current source fingerprint. At Confirm, reload the session's effective source and check the active review and source binding. Extract a pure BPD V3 review/commit core that accepts the trusted source and the existing adapter; both the legacy V3 route and conversation route call this core. It reuses `exactBenchVariant`, `buildBenchVariantRows` and adapter `commit` for the one linked draft variant and pending manual cue. Do not duplicate platform-row writes. The conversation store keeps only the successful token-to-adapter identity pointer needed to return the original creation receipt on exact retry. A replaced or stale unconfirmed review cannot be used. Legacy BPD V1/V2/V3 signed wires and verifier, `/schedule/review`, `/schedule/confirm` and original-fixture loading stay unchanged. No in-process HTTP call or second variant store is needed. The receipt does not mean the post was published or added to a durable Schedule Rail.
